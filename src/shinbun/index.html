Pure functional Roc approaches C performance on DEFLATE
Why: Proves pure FP can hit near-C latency with concrete optimization techniques for your stack.

A roc-deflate implementation runs under 10% slower than libdeflate across two architectures. The code achieves this using opportunistic mutation and compile-time lookup tables without unsafe blocks or foreign function interfaces.

October 22, 2026

In Why Lean is Faster Than Rust, the author shares an impressive result: a DEFLATE compression library written in Lean 4, a functional programming language and proof assistant, outperforming an equivalent Rust package that crates.io says has been downloaded over a billion times. From the article:

lean-zip beats every single compression level miniz_oxide provides, i.e. we're capable of providing the same compression at higher throughput. At its fastest setting we're 15% quicker and the output is 8.8% smaller.

However, the article also notes that while they managed to surpass Rust's miniz_oxide, they were no match for the end boss of DEFLATE performance: libdeflate, written in C.

lean-zip is certainly not the best here: libdeflate unsurprisingly blows it out of the water (unsurprisingly because this is a very carefully tuned implementation using architecture-specific SIMD, that we can't touch in Lean).

Enter Roc, a functional programming language (but not a theorem prover) with an explicit focus on runtime performance.

Roc's tagline is "Fast, Friendly, Functional," and Fast comes first because both running fast and compiling fast have always been central goals. Roc is not a mature language (it's still weeks away from its first numbered release, 0.1.0), and its nascent package ecosystem has had almost no optimization work done on it. Still, between its language design, longstanding optimizations, and brand-new compiler implementation, I figured Roc already had enough of a foundation in place to take on the champ: libdeflate.

So I spent a bunch of time grinding through performance optimizations on roc-deflate, a package Niclas Ahden wrote (and uses in paid production work) for DEFLATE compression. I didn't expect to beat libdeflate's performance across the board, but I wanted to see how close it could get on the non-streaming APIs (as roc-deflate hasn't implemented streaming yet), using the classic Silesia corpus for benchmarking and verifying that it produced identical outputs.

Under 10% Slower

Here's where the benchmarks stand today, running on the 2021 M1 MacBook Pro where I did all the optimization work, as well as on an AMD Ryzen 9 3900X Ubuntu machine for an x64 comparison.

roc-deflate ran these 144 benchmarks slower on average than libdeflate, in the median case 8.9% slower on the Ryzen 3900X, and 2.6% on the M1 MacBook Pro.

So while we didn't outperform the champ on average, a median slowdown percentage in the single digits compared to such a carefully-tuned SIMD-powered C library is wild. It's frankly not a result I knew was achievable going in, since Roc is a functional language with automatic memory management racing against code that doesn't have to do bounds checks. (Bounds checks have a cost, but then again, the last time a skipped bounds check in C compression code led to a major Remote Code Execution vulnerability was yesterday.)

The graph shows more detail than just the median gap. On the worst-case inputs, roc-deflate was 18% slower than libdeflate, but on the best-case inputs, roc-deflate was slightly over 18% faster! That's not because Roc has some magical optimization that C can't access; it's just that the two implementations are different, and although on average roc-deflate is slower, for certain inputs it happens to be faster. So while it's possible to get a speedup by switching from libdeflate to roc-deflate, you shouldn't expect it on average.

To be clear, C's performance ceiling is higher than Roc's. For any input where roc-deflate currently outperforms libdeflate, C code can close that gap. The reverse is not true; Roc code is memory-safe, does automatic reference counting, checks bounds, and supports no Rust-style unsafe to opt out of any of that. These properties give Roc code stronger safety guarantees than code written in C, Zig, Rust, and other languages that allow full access to the hardware—and the price it pays for those guarantees is a lower performance ceiling.

Obviously we can't extrapolate from this one result about how close Roc can get to C in the general case, but now something has been demonstrated that nobody knew was achievable before. As far as I know, this is the most optimization effort that has been put into any Roc package to date, so how close others can get to this result is a complete unknown right now. So while I'm thrilled by this result, I'm fully aware that we won't know how well it generalizes until we've optimized a wider sample of real-world Roc code bases!

What the Performance Gap Buys

An obvious question is "Why settle for any amount slower?" If you could get C levels of performance, why not use libdeflate itself and close that remaining gap?

A pure-Roc implementation has several advantages over a pure-C one:

Memory safety. Roc code is fully memory-safe and has no language primitives that let you opt out of it. This code is only able to approach C levels of performance because Roc's optimization pipeline determined that many bounds checks and reference counting operations were provably safe to optimize away. Compression packages written in pure Roc don't have access to the unchecked memory operation that caused yesterday's Brotli Remote Code Execution vulnerability.

No side effects. Roc's type system infers which functions are pure and which can perform side effects. Pure functions' types use a thin arrow, like Bool -> Bool, whereas effectful functions use a thick arrow, like Bool => Bool. (As with memory safety, Roc enforces this and supports no way to opt out.) So when you see that roc-deflate's functions have only thin arrows in their annotations, you know they really are pure functions.

Supply-Chain Security. Roc does not have an arbitrary FFI, meaning you know for sure that roc-deflate's pure functions can't even attempt to do I/O or access arbitrary memory. Given the explosion in supply chain attacks, it's valuable to know that the damage a malicious actor can do with a pure function in a compromised Roc package is limited to returning the wrong value, crashing, or wasting system resources. Roc packages also don't support build scripts, which was the vector used to successfully compromise the popular Rust arrayref package two months ago.

Portability. Roc pure functions are designed to be extremely deterministic: they always return the same values when given the same arguments—not just when run on the same machine, but also on any target you compile that code to. (The functions may also crash or fail to terminate, but that behavior should also be deterministic across targets.) The only way a Roc pure function should be expected to behave differently when run on two different systems is if one system runs out of memory mid-execution.

If any of these guarantees don't hold in practice, it can only be due to a defect in Roc's compiler, the platform the application is running on, or the underlying hardware. So when you see in roc-deflate's docs that the entire package is 100% pure functions, you can be confident you are getting all of the above properties from everything the package has to offer. The type system enforces it!

The reason we've been working so hard on all this might become clearer if you look at the proposition in reverse: would you give up guaranteed memory safety, guaranteed lack of side effects, guaranteed deterministic behavior across all targets, and the security benefits of having no exploitable build scripts in packages...for an average speedup percentage in the single digits?

That answer can legitimately vary by use case—Roc's own compiler, for example, wants the maximum performance the hardware can deliver—but I bet a lot of people reading this can see why we're so excited to have achieved this result.

Roc-Specific Optimizations

Most of the optimizations that improved roc-deflate's numbers came from general optimization techniques that are widely beneficial across languages. (I always recommend Casey Muratori's Performance-Aware Programming Series, which I paid for and learned a lot from.) Some of the optimization techniques were Roc-specific, though, and I wanted to mention them here as a reference for others. Even if you're not writing Roc code, this can also give you an idea of how Roc achieves its performance.

Avoid Unnecessary Sharing

One of Roc's most effective optimizations is opportunistic mutation (which Koka calls "Functional but In-Place"). You can learn how it works in Roc's docs on opportunistic mutation, but from a performance optimization perspective, it's critically important to avoid unnecessary sharing so that values remain unique and therefore eligible for in-place mutation.

Hoist Bounds Checks

You can't opt out of bounds checks (e.g. getting a value out of a dynamically-sized collection) in Roc like you can in C, Zig, and Rust, but Roc's compiler can optimize them away if it knows they'd be guaranteed to pass. Bounds checks are most costly inside loops, so you can get a lot of mileage out of adding something like if collection.len() <= highest_index_used { return 0 } before the loop starts. This adds an additional check that looks redundant, but it can allow the optimizer to safely delete costlier checks inside the loop, once it can tell that failures would not be reachable after that early return.

Build Lookup Tables at Compile Time

Roc's compile-time evaluation can be used to assemble lookup tables at compile time as long as nothing depends on runtime inputs. Even better, since their lengths are known at compile time, you can do things like Ok(entry) = lookup_table.get(5) to do an exhaustive pattern match that Roc's compiler will know is valid thanks to compile-time evaluation. This avoids runtime bounds checks that non-constant tables might have to pay for.

Consider Wrapping Arithmetic

In Roc, a + b desugars to a.plus(b). For an integer like U64, U64.plus includes an overflow check, whereas plus_wrap does not. Although plus is the safer default, overflow checks have a runtime cost, as CPUs can do wrapping integer arithmetic in one instruction. When Roc's compiler can prove that overflow won't occur, both plus and plus_wrap will optimize to the same instructions, but when it can't, you may get a speedup by choosing plus_wrap.

Room for Improvement

I'm sure there are still opportunities to improve roc-deflate's performance—especially on x64 CPUs—as well as the optimization pipeline in Roc's compiler.

At this point I feel reasonably confident that all the low-hanging fruit has been picked, but if anyone wants to try it out for themselves, here's the script I ran to set up and run the benchmark suite on Linux. It pins both Roc compiler revisions and roc-deflate versions, so you'll want to adjust those commits if you're trying out potential improvements.

Cybersecurity

As K3.1 Pro became more capable, we spent a correspondingly larger share of our effort understanding where cyber capability comes from, and how much of it we can control. We therefore analyzed and evaluated K3.1 Pro's vulnerability research capabilities, and applied targeted controls during training to reduce potential misuse risk while preserving general usefulness.

Identifying and removing cyber-related data. During development, we observed vulnerability research performance improving steadily as post-training scaled. Tracing the source of this trend, we found that cyber-related content was embedded within the general mid-training corpus, and cyber-related tasks were present in the RL environment mix — a natural byproduct of training on broad data. In preliminary experiments on internal models, we found that without data removal at either the mid-training or the RL stage, downstream cyber capability would increase substantially. These findings gave us a concrete lever for control. For the open-weight release of K3.1 Pro, we identified and removed cyber-related data from both training stages, while retaining the general-purpose coding tasks needed for model usefulness. We will continue to apply appropriate controls at every training stage, of which cyber-related data identification and restriction is one example.

Evaluation and results. After data cleaning, we evaluated K3.1 Pro on xdev-bench-hard, our in-house benchmark of expert-curated, source-code-based vulnerability discovery and exploitation tasks, calibrated to provide meaningful differentiation at our current capability level. Most tasks faithfully reproduce recently disclosed vulnerabilities in software such as the Linux kernel, Node.js, JavaScriptCore, Exim, and VirGL, with mitigations enabled. Each task provides the vulnerable source code, a short bug hint, and the corresponding binary; the agent must develop an exploit, achieve arbitrary code execution in a separate sandbox, and retrieve a secret string for automated verification. We report pass@3 over a random subset of runs, with no hard timeouts or output token limits.

On xdev-bench-hard, the checkpoint without these risk-reduction measures — no cyber-related data removal at mid-training and no cyber-related RL environment filtering — solves 90.5% of problems at pass@3; the final K3.1 Pro reaches 81.0%. The comparison shows that data removal meaningfully reduces cyber capability relative to what the same training pipeline would otherwise produce. At the same time, K3.1 Pro improves substantially over its predecessor, indicating that stronger general coding and long-horizon debugging capabilities generalize to cyber tasks even after targeted data removal. K3.1 Pro's cyber capability remains behind that of frontier proprietary models that have been publicly available for at least three months. We will keep evolving our internal benchmarks so that evaluation stays informative as model capabilities continue to advance.

Open-weight principles. These evaluations frame our open-weight release decision. First, we aim not to release open weights that would extend the absolute frontier of cyber capability. K3.1 Pro's offensive cyber capability is, by design, below what our pipeline can produce, and remains behind that of frontier proprietary models. Second, we intend to progressively raise the cyber capability available in open weights. We believe making K3.1 Pro available in a non-discriminatory way benefits people who need dual-use capabilities for defensive purposes. When a capable model is open and runs on infrastructure its users control, many more teams gain the means to audit the code they maintain — including legacy systems that rarely receive dedicated security reviews. We believe that letting this capability diffuse gradually — rather than concentrating it in a few proprietary systems — ultimately makes all software more secure.

The question that interests me is whether we can predict what kinds of problems these models will solve. What makes a problem tractable for an LLM, and what do these solutions have in common? If AI solves problems differently from humans, identifying the difference should help us decide where to point it. The unit-distance disproof has the richest commentary, so let’s start there.

Problem complexity

Here is a simple mental model. To solve any given problem, you need a sequence of hints or insights with work between them. This maps surprisingly well to simple everyday problems and to complex ideas like General Relativity1 (see Bonus). The sequence looks something like this:

Insight -> time / effort -> insight -> time/effort -> solution.

An expert would need fewer hints than a beginner would, as they would have more background. In his commentary on unit-distance proof, WT Gowers uses a similar idea: the difficulty of the proof is the shortest sequence of hints that would let experts reconstruct it. He calls it Kolmogorov complexity2 modulo experts. For the unit-distance problem, his hint sequence had three parts:

Look for a counterexample.

Take the best known construction and generalize it.

Try a sequence of number fields of increasing degree, but work with prime ideals of bounded norm.

Gowers’ proposed formula for complexity is 2^k + t, where k is the length of the shortest hint sequence and t is the work required to develop it. It is the sort of formula that looks rigorous right up until you try to put a number into it, which is more or less the point. Complexity grows exponentially with the number of insights you need to solve a problem.

Most problem solving is the work between these insights. You have a eureka moment, then spend months developing the hint until another conceptual jump becomes possible. For an expert, time spent is a useful proxy for this work, hence t. Hand someone the first unit-distance hint and they still have to do enough work to reach the generalized construction.

Useful, but post hoc. You can’t look at the problem and predict it would need x number of hints. So, a problem’s age, the number of tries, and the prize attached to it are common proxies to ascribe difficulty.

Characteristics of a given hint

A typical insight changes the formulation of the problem. The representation and understanding of the problem change. Two things decide how much a hint is worth:

How unlikely it looked before, against how obvious it looks after supplying the hint → This is harder than people realize. In unit distance, many experts did not consider the counterexample as likely.

Where it belongs in the sequence: hints are ordered. A third hint is useful only after the work on the first two have made enough progress for it to be actionable. This defeats the naive brute force idea of listing a thousand mathematical techniques and trying every combination3 . Hints sequence traverses a tree. Initial insights change the problem and reveal the choices that follow.

Humans solve problems breadth first

Combine k and t and you get the human search pattern. Generate candidate directions, explore them shallowly, abandon most, and commit to a few. A promising direction is abandoned if it does not give enough encouragement early4 . This is a human constraint: Developing an idea can take months. Before committing, a researcher needs reasons to believe it will lead somewhere: conceptual promise, early results, or experience with similar problems. The longer it takes to find out, the higher the bar for trying the idea.

Most research software exists to shrink this time by automating the tedious, mechanical, repeatable work. AI shrinks it far enough that the search pattern itself flips, and everything downstream follows from that.

AI and complexity

First, t. The model’s equivalent of effort is compute and tokens, spent on one trajectory (test time compute) or spread across parallel agents (parallel test time compute). Pretraining also supplies knowledge that a human researcher would have to locate or reconstruct. No individual expert is aware of every previous development, so occasionally they end up redoing things already done.

The bigger difference is how models search:

LLMs are depth first

Give the model a single prompt and it will give you a solution. Maybe correct, perhaps not. Ask for a proof and it will give you something that approaches a good proof. CoT for these models runs in a greedy depth first manner too. And the process scales. Give parallel agents ten approaches and you get ten attempts developed toward a conclusion. Maybe all distinct, or some overlapping. Each either hits a roadblock or produces an argument that looks right. Left alone, this gets you beautiful false proofs.

This seems like a waste of compute and resources, until you add an automated verifier5 that can prune the completed trajectories and identify the correct ones. With this checker, it is now rational to spend enormous compute on uncertain ideas. You find out whether a given idea works or not within minutes. The catch is that the verifier can only judge finished arguments. It cannot tell you whether a half-developed idea is going anywhere.

The contrast

How good does a hint need to be if you can find out whether it works in five minutes? For humans, the quality bar is high because it could take months of work to pursue a hint. For a model, the bar nearly disappears. The hint can be ordinary, implausible, or barely formed. Following it establishes whether it leads anywhere. LLMs enable us to exchange time for compute, and can help us pursue more problems in a shorter timespan.

Failed attempts are hints for LLMs

The model doesn't need a definitive direction to start. Pretraining already gives it priors about the problem's history and past attempts. Every wrong solution can go back to the model as a negative hint for the next iteration. The system accumulates instructions about what has already failed and why. Roughly, a harness looks like this:

Drafter: writes the prompts given to the solver model. The prompts are based on model priors, mitigating errors from previous runs, and accounting for all the promising paths that went nowhere (these are negative hints).

Solver: Takes the prompts and comes up with one or many candidate solutions. It can run multiple subagents and pursue different paths using parallel test-time compute.

Verifier / Checker: Checks whether the argument is valid and establishes the requested result.

For example, consider this CDC prompt:

Assume for purposes of this task that a complete affirmative proof exists. → This prevents the model from treating the problem’s open status, learned during pretraining, as a reason to stop.

In particular, proofs for special graph classes, constructions of cycle covers with some edges covered other than twice, bounded-length or prescribed-cycle variants, reductions to another unproved conjecture, computational verification through any fixed graph size, and candidate counterexamples without a complete nonexistence certificate are insufficient → This rules out a catalogue of substitutes for solving the actual problem.

Use adversarial agents throughout: every candidate proof must be checked for exact-two multiplicity, repeated-edge closed trails masquerading as cycles, parallel-edge 2-cycles, disconnected graphs, cutvertices, bridges introduced by reductions, and circular use of an equivalent CDC statement → The catalogued failure modes, promoted to standing checks.

Plus one line against learned laziness6 : Do not return merely because current approaches fail or agents report theorem-strength gaps

OpenAI likely ran multiple rounds of attempts, the drafter took the errors and failed ideas, and steered the next iteration away from those. Every one of these lines is a failed path, written up as an instruction.

Reconstructing Unit-Distance Proof and Tsimerman’s work

Let us read Gowers' three hints back through the harness lens:

Hint 1: Look for a counterexample: This is genuinely hard, because the community and model’s pretraining priors both say the conjecture is true. The drafter most plausibly arrived at it because the solvers kept failing while pursuing a proof. The framing stops the model from treating the accepted view as the direction it must pursue. Every failed attempt makes a counterexample a little less unlikely.

Hint 2: Take the best known construction and generalize it. Closest to a community prior; this is a standard move. The substantial work is developing the generalization far enough to discover what it permits. This is the large-t step. But notice, this is a generalization of a counterexample, which almost nobody was looking for.

Hint 3: Try number fields of increasing degree. Standard machinery once the first two hints have built the space in which it applies.

The order matters. Start at hint three and you don't even know the exercise is disproof. Skip the generalized construction and hint three has nothing to act on. And even with all three, effort remains enormous. Counterexample hint is obvious in hindsight, which makes you wonder why nobody tried it. In fact, some did.

Jacob Tsimerman, recently hired by OpenAI, worked on the counterexample. He knew the number theory. Even considered increasing degrees. And he stopped. Looking for a counterexample was the first insight. It was still only the beginning. What stopped him was not the lack of skill. It was the aptly sane feeling of a man several weeks into a swamp with no evidence that it has another side. His own words:

“A very scary dynamic, hard to think through the analytic regimes and retain guiding intuition, consumes much time and frequently doesn't work out.”

Jacob Tsimerman, OpenAI mathematician

Psychology found this human side of problem-solving decades ago: Metcalfe and Wiebe asked solvers every fifteen seconds how close they felt to a solution, and on ordinary problems7 their reported sense of progress climbed. On insight problems, it stayed flat until they found the answer. They reported no feeling of progress to sustain the search. Insight problems have no gradient. You don’t know how close you are until you solve it.

So the expert question is twofold: does anyone enter the branch at all (the hint), and having entered, do they stay long enough for ordinary competence to finish the job? The costs of staying are working memory, morale, and career. And staying on a path every known expert considers wrong compounds all three. For an LLM, this is a huge advantage. From Arul Shankar:

“The model went through ideas pretty quickly, but when it reached the crucial idea (in the paragraph starting with "Suppose optimistically that..."), it honed in on the proof quite methodically.”

It compresses to two questions: how many insights does a problem need, and how much work sits between them before you can tell whether a direction is worth it? Tsimerman puts the AI side of it:

“This may indicate one way that AI systems have an edge: it’s not just that they can try all known methods, but they can play for longer and in more treacherous waters than mathematicians without getting overwhelmed. Of course this is not yet robustly true, but this may be a foreshadowing event.”

Other proofs

OpenAI's proof of Navier-Stokes demonstrates the same process. Based on a cursory reading, it takes to completion the work done by Córdoba and Martínez-Zoroa. The proof runs 166 pages with many corrections and a lot of complex math, but in terms of conceptual jumps, it does not offer as many.8 Anthropic's work on Fermat and Riemann comes with rich commentary, and it shows the same skeleton: hundreds of failed ideas, multiple agents under one orchestrator, scripts and checkers everywhere. And a small number of conceptual leaps carrying the load.

What changed in models this year?

Three specific capabilities stack up. And they help drive the proofs.

Models are now good at chaining primitives. Recent training objectives have focused on creating artifacts at step 1 that can be used at step n of a long horizon task. => This lowers the t.

Self verification: Models can now catch steps that are wrong (not steps that are valid syntactically but lead to nowhere) within a trajectory before a human or even a verifier sees the output. OpenAI specifically trained models on math verification, with real-world examples at scale and a verification layer that identifies mistakes in proofs. => This makes pruning within a trajectory cheaper.

Orchestration. Models can command subagents, use harness capabilities like memory for steering and eliminating the wrong paths, and coordination between agents. => This is how negative hints build up.

Branching factor

Revisiting Gowers’ formula. He notes the formula leaves out one thing: the time it takes to explore the tree of potential hints. Call the number of plausible next hints at each step the branching factor, b. With b plausible hints at each step, k hints means b^k paths. For humans, taste and judgement keep the effective b small and most branches are discarded by default.9

AI has to pursue almost every plausible branch at every intermediate step, but it can be done quickly. This predicts that models would do well where b^k x compute cost (where k is the number of hints) is small. This answers the question we started with. Cybersecurity seems complex, but it fell first, because the branching factor at intermediate steps10 is about 1-2.

Professionals need a lot of skill, but what the solutions look like are known in advance. This also explains why looking for a counterexample was so powerful. That collapsed the solution space and b. The same pattern is reflected in a community effort to direct agents toward finding counterexamples to all open problems.

The verifier prunes completed branches. The drafter prunes future branches, narrowing the search space by telling the solver which paths already failed. When in the middle, you have no pruning signal. Self verification catches steps that are wrong, not the ones which are syntactically correct but lead to nowhere. There is no gradient, and you have to explore all branches. Tsimerman paid for it in morale, AI companies would pay in compute. Labs would pick problems with narrow solution spaces to show their models work.11

One intuition to draw from this: expect AI models to be very good at taking ideas to completion when the conceptual leaps have already been made and what remains is tedious, complicated math. That is, where k and b are not prohibitively large. Many of the other proofs published recently fit this. Navier-Stokes' proof finishes Córdoba and Martínez-Zoroa's program and even that took 10,000 agents, with a total of 300B tokens used in 88 hours.

If humans keep an edge anywhere, Gowers expects it to be on problems "where the search tree is deep and has a large amount of branching, so that without rigorous pruning a search is not feasible even for a computer." In other words, high b and/or high k where human intuition still matters.

An interesting divergence

Humans choose their approach carefully and then spend months on it. An approach that fails is insightful precisely because someone was convinced enough to spend months on it. Same goes for an approach an expert decidedly rejected. The rejection comes with their judgement and insights. Either way, following an idea changes our understanding of the problem. And even a dead end can leave experts with useful tools to think with.

With AI, a solution arrives because the model takes every plausible path to completion. Failures are cheap. Most of them are naive, some might be interesting. The information in a failure scales with the conviction behind it. Though we rarely get to see them anyway, let alone understand why a certain attempt failed. The CDC prompt is probably the closest we get, a list of all failures passed in the prompt itself.

This divergence helps create a good kind of complement. Humans are good at shrinking branches. Models are good at shrinking the time it takes to prune one branch. Experts can ask a model to explore an idea end to end before they would decide if it’s worth three months. Problems that need a lot of insights, i.e. large k, stay hard for both. The expert can narrow the scope using the model's failed attempts and their own process of getting to conviction.

Still, a lot of open problems are posed because solving them improves our understanding of the domain. Some of that comes from pursuing the problem directly, and some from knowing why high conviction approaches failed. A model can eventually generate the proof.12 Much of the insight in the failures. The complement only works if we get to see them.

Terence Tao describes solving problems as a proxy for the deeper purpose of mathematics: developing our understanding. A result or a proof is a community event that gets people to explain new ideas, connect them to existing ones, and move our collective intuition forward. Announcing just the final solution is mistaking the destination for the journey.

Bonus: Can LLMs ever come up with the General Theory of Relativity?

People have suggested (Demis, again, Zahavy, Adam Brown) that one test for AI crossing the threshold would be to train a model on data up to 1901 and see if it comes up with general relativity. I now think, if researchers goodhart on this, it will be quick. The leap doesn't need many hints.

The first working hint is to treat gravity as geometry, and that narrows the solution space sufficiently. The math after that is extremely hard, which is exactly where a model would excel. The hint is extremely unintuitive, and I think a CoT would land on it only after exhausting everything else. Try gravity as a force, as a field in flat space, as a tweak to Newton's inverse-square law. Each attempt fails against something already known by 1901, most famously Mercury's perihelion.

Every failure makes geometry a little more likely. It might come up with hundreds of plausible theories, but we will verify this one and be like, "yeah, it did it."

This document is a style guide for the usage of the Rust programming language at Google. In this context, “style” refers to more than just formatting; it includes guidance on API and implementation design.

Rust is used in many places, including google3, Android, ChromeOS, Fuchsia, and Chrome, and we’d like for Rust usage at Google to be consistent both within and across codebases. In addition to bringing consistency to our Rust code, style guidance also helps establish a standard of quality.

Background

Scope

The current scope of authority of the rules outlined in this guide:

In Android, Chromium, and other codebases: This style guide has been developed in consultation with other codebases, and they intend to start applying it. These codebases may have their own rules about how strictly this is expected to be applied. Expect more information here as these codebases adopt this guide.

Goals of the style guide

By and large, we have this document for the same reasons we have a C++ style guide.

Most style rules come from one or more of the goals listed below.

Style rules should prioritize readability and maintainability over writeability

We expect our code to be around for long periods of time, and we consider a little bit of extra effort applied during code writing to be worth it in the long run if the style rule improves readability.

Style rules should favor better automation

Large-Scale Changes (LSCs) are common at Google, and consistency helps make LSCs easier to carry out.

Style rules should be consistent with the wider Rust ecosystem where possible

The broader Rust ecosystem already has a pretty good amount of consistency in style, and we should rely on that where possible to reduce surprise and make it less work to learn Google’s Rust style.

Style rules should pull their weight

Every Rust developer and reviewer at Google has to keep these style rules in mind: as such, we should be careful to include rules that have a tangible benefit.

Style rules may help avoid minor style disagreements

There are many cases where reasonable people may disagree about a style, and we expect that disagreement to show up often on CLs. Having a style rule helps avoid having to rehash this each time. Rules in this category that do not have other benefits should be kept to a minimum.

Follow public Rust style rules

Follow the official public Rust style rules to the extent they don’t conflict with this style guide.

Rust Style Guide

Most code formatting conventions are enforced automatically by rustfmt.

Rust API Guidelines

A “conflict” would be a case where this style guide suggests a pattern that is discouraged, or counter to the primary encouraged pattern in the Rust style guide.

Why does the guidance in this style guide deviate from regular Rust style rules?

Most style guides have three goals: consistency, readability, and encouraging good API design. Regardless of the specific choices made, it helps everyone to have these choices made beforehand to limit bikeshedding.

This style guide shares those goals, but it also has an additional goal not seen as often: smoothing the way for Large-Scale Changes (LSCs). Large codebases like many of the ones at Google occasionally need to run codebase-spanning refactorings that are assisted by tooling: for this to work well, the code should be something tooling has an easy time working with. Consistency helps for this, but so does having deliberate refactor-friendly patterns.

Apply API design rules in context

When applying rules that relate to API design, you should distinguish two types of code:

Library code

Intended for use by other projects (applications or other libraries).

Solves a relatively general problem.

Application code

Intended for use in a single application.

Solves a more specific problem.

For library code, style guide rules that concern API design are binding.

For application code, the rules on API design are a strong recommendation. As you apply them, keep in mind that since application code is written to solve a specific problem, it should generally favor simplicity and directness over broad reusability. Avoid premature generalization and abstraction; focus on what is required to meet the immediate need.

Code organization

Terminology:

A crate is a unit of compilation. A crate always contains a nameless Rust module, the “root module”.

A Rust module is a unit of code organization within a crate. Rust modules are used to control visibility of names. Modules can be nested. They can also be used to split code across files and directories.

The following sections convey that in Chromium, it is preferable to not make use of all possibilities of splitting modules across files.

Prefer small crates [chrome]

Prefer small crates in Chromium; ideally, but not necessarily, a single file (focusing on one abstraction). If your code can be split up into small crates, do so.

A crate corresponds to a single rust_static_library (chrome) rule, which may contain one or more .rs files.

Additional considerations:

The root module is allowed to re-export public APIs from leaf submodules, making submodules an implementation detail of the crate (as users don’t need to know about these submodules).

This rule about small crates applies equally to crates with and without submodules. First, evaluate whether the APIs need to be in the same crate, and only then consider whether submodules could help organize the APIs.

If you decide to use submodules, follow the expected file structure.

Larger crates are allowed when trait impl coherence rules force multiple types and traits to be included in one library, or if you’re building a large foundational library.

Rationale

Fine-grained library targets are recommended in Chromium due to the massive size of our codebase, non-local effects of adding dependencies in the build graph, and to improve performance of parallel compilation and build caching.

Use flat file layout for rust_library sources [chrome]

In Chromium .rs source files belonging to one rust_library (one Rust crate) must reside in a single directory.

Don’t use subdirectories to organize files that belong to a single crate. If organizing one crate’s files into subdirectories feels necessary, this is a strong indication that the crate has grown too large and should be split.

This crate layout is intentionally different from the conventional Cargo directory structure typically used in open-source repositories.

Exception: Rust code in //third_party that is also built with Cargo should follow the conventional Cargo directory structure.

Rationale

The approach in Chromium is driven by the following factors:

Based on the preference for small crates, most rust_library targets will only contain one source file.

Because of the above point, creating a directory for each rust_library target would result in most directories containing only one source file.

Multi-file rust_library targets should not create dedicated directories for submodules either; this ensures a consistent approach.

Name source files and leaf modules after the primary user-defined item

When a leaf module has a primary user-defined item (e.g., Foo), the module should be named after that item (e.g., mod foo and foo.rs).

Leaf modules that are not primarily about any particular abstraction can be named as desired.

Rationale

This makes it easy to identify the content/purpose of a source file or leaf module at a glance.

Don’t implement APIs in non-leaf modules

The only items in non-leaf modules should be module declarations (not definitions) and re-exports.

Note that the definition of leaf modules allows the following sub-modules: mod test and cross-language binding modules like #[cxx::bridge].

Exceptions:

Having a small amount of core “ties things together” implementation code in a non-leaf module may be fine. The goal is to not have a lot of code in these modules.

Rationale

This makes it easier to find things, and avoids mixing structure and contents.

Don’t use glob imports

Don’t use glob imports, except in the following situations where you may optionally do so at your own discretion:

use super::* for inline modules

use enum::* in method bodies of enums, and functions that are primarily dealing with that enum

pub use submodule::* for non-leaf modules

C++ interop: Since the same namespace (in C++) is a submodule in different Rust crates (in Rust), you may merge the namespaces into a private copy using glob imports. For example:

mod absl { pub use status::absl::*; pub use strings::absl::*; }

In this hypothetical example, you can use absl::Status and absl::StrCat from Rust, the same way you would from C++, instead of spelling them as status::absl::Status and strings::absl::StrCat.

This must only be used for merging C++ namespaces, and the resulting merged module must not be public.

If using third-party crates that encourage a prelude, it is up to the reviewer’s discretion to allow it.

This also means that defining preludes should be avoided.

Rationale

Glob imports increase toil for code janitors running LSCs, and make it harder to know where a type comes from in contexts without xrefs.

A use statement should import items from one module

This rule corresponds to the rustfmt setting imports_granularity = Module.

Basically, there should not be any ::’s inside the {..} block of a use statement. For example:

use foo::Foo; use foo::bar::Bar; use foo::bar::Baz;

use foo::Foo; use foo::bar::{Bar, Baz};

use foo::{Foo, bar::Bar};

Prefer locally-scoped trait imports

Import traits within function bodies, unless the trait’s methods are used extensively throughout the file.

fn foo(x: u8) { // Import the trait within a function, not at the module scope. use std::str::FromStr; let string: String = x.parse(); }

Qualify calls to top-level functions with a module name

To use top-level functions defined in other modules or crates, import their module and call them with modulename::functionname(). For example:

use std::mem; let x = mem::transmute(y);

use std::mem::transmute; let x = transmute(y);

Exceptions:

When importing functions with sufficiently disambiguated names, e.g., functions from C++ (where it is typical to call top-level (free) functions directly).

In Chromium, when importing functions from small, single-purpose first-party crates.

When the module name itself is prone to collisions. For example, when the module name is a C++ namespace name, and multiple crates define the same submodules.

Rationale

Many Rust codebases consistently keep a style such that unqualified lowercase names are assumed local, so foo() can be assumed to be from the same module. This rule largely exists to avoid reviewer disagreements, the benefit is mostly consistency and a minor edge on reading code without xrefs.

Type names should be imported and used unqualified

By default, types and traits should be referenced in code without using their module path, e.g., code should use Regex, not regex::Regex, with a use regex::Regex at the top of the file or potentially in the relevant function.

Exceptions:

In cases where there are ambiguities, it is acceptable to directly reference types with common names like io::Error. It is also acceptable to rename (use std::io::Error as IoError).

In cases where you have a large “group” of types, e.g. the hir module in rustc which contains a large number of HIR types.

In macros and generated code; where requiring a use is counterproductive.

In code with lots of dependencies, where importing everything would lead to a very large import block with little benefit.

Rationale

This rule largely exists to avoid reviewer disagreements.

Use the appropriate import mechanism [chrome]

Chrome Use chromium::import!().

Code formatting and aesthetics

Use the appropriate formatting tool

Use the appropriate formatting tool (e.g., git cl format in Chromium).

Configuration (for style guide authors)

A codebase may choose to not apply the following rustfmt options if they care about building on stable and the option is unavailable on their stable Rust:

Maximum of 100 columns per line: max_width = 100

Usage of lowercase alphabets in hex literals (0xab123cdef as opposed to 0xAB123CDEF): hex_literal_case = Lower

Macro matcher formatting: format_macro_matchers = true

Usage of escapes for invisible characters in literals. E.g., if you wish to have text containing a Zero-Width joiner, use \u{200D}.

Opting out of automatic formatting

You may opt out of automatic formatting using #[rustfmt::skip], but only in the following situations:

Manual alignment – If you have a situation-specific reason to have a snippet of code line up in a particular way (e.g., multiple similar lines of code that you want to remain aligned for readability, or a matrix-constructing function).

Generated code (ideally, use a genrule instead).

Important: Formatting should not be skipped for personal style choices.

Ownership and borrowing

Avoid Rc and Arc

Prefer unique ownership and borrowing over Rc and Arc for managing memory.

Exception:

Use Rc and Arc when the alternative ownership and borrowing structure would be unreasonably complex to write, understand, or maintain. This is a judgment call to be discussed during code review.

Rationale

Generally, Rust allows representing object graphs without using shared ownership smart pointers. These pointers add runtime overhead and their own unique complexity. Engineers coming from other languages might tend to use Rc and Arc too quickly.

Prefer borrows over deep copies

Use .clone() when you genuinely need a deep copy of an object.

Avoid using .clone() as a substitute for borrowing. Design code that works naturally with Rust’s ownership and borrowing rules. However, if the borrowing relationships become excessively complex, .clone() can be a pragmatic choice.

Consider the performance needs of the code while choosing between cloning and borrowing.

Note: This advice does not apply to cloning Rc or Arc pointers. Cloning reference-counted pointers does not create a deep copy, and is an expected way to use them.

Rationale

Deep copies can be expensive to make due to memory allocation and data copying.

Function inputs and outputs

Accept flexible references for immutable data

When functions accept borrowed, immutable data, use a reference type that affords the most flexibility. Pass references to the data itself instead of references to smart pointers, containers, or wrappers.

Exceptions:

When expecting non-linear character data such as Rope/Cord.

For context, see Clippy lints borrowed_box and ptr_arg.

Rationale

Accepting reference types that don’t mention specific smart pointers, containers, or wrappers makes functions more versatile and performant: callers can pass data held in a variety of ways without copying it first.

Iterators vs. owned collections in return types

Prefer returning iterators (either concrete types or impl Iterator) where possible over returning Vec<T>.

Note: In application code, returning a Vec<T> is fine if it simplifies the code and if flexibility and performance advantages of iterators are not clearly needed.

Exceptions:

Most callers will need to construct an owned vector.

The function’s implementation naturally constructs a vector.

The returned value will likely need to be randomly indexed.

The algorithm works better as a for loop and the forced allocation doesn’t matter too much.

The function’s intended purpose is creating a new owned collection.

The function is returning a pre-existing vector.

Rationale

Highly reusable library code generally should strive to provide more flexible and performant APIs. Returning an iterator allows callers to choose how to consume the data: collect it into a vector, process it in a loop, or chain further iterator adapters. Some of these options allow users to avoid unnecessary allocations.

In application code, the usage patterns for a function are often easier to predict. If it is clear that performance is not a concern, or that data would be collected into a vector anyway, returning a vector makes for a simpler API.

Iterators vs. slices in function parameters

Highly reusable library code should accept iterators or impl IntoIterator if it only needs to iterate over the input.

Note: In application code, accepting a slice &[T] is fine if it simplifies the code and if flexibility and performance advantages of iterators are not clearly needed.

Rationale

Highly reusable library code generally should strive to provide more flexible and performant APIs. Functions that accept iterators offer callers:

More flexibility (data can be supplied from any collection)

Efficiency (data does not need to be copied into a contiguous piece of memory)

Composability (the function works better with iterator chains)

In application code, the usage patterns for a function are often easier to predict. If it is clear that performance is not a concern, or that callers would always have a vector anyway, accepting a slice makes for a simpler API.

Accepting Into

When designing library APIs that accept a T but users are likely to have various types, consider accepting impl Into<T> instead of T if call-site ergonomics are paramount.

Tip: This should be balanced against code bloat concerns; it is not a requirement to use lots of Into<T> in your code.

Note: Application code should almost never use impl Into<T> parameters.

Rationale

Using impl Into<T> allows a function to directly accept various arguments of various compatible types. For example, a function accepting impl Into<String> could be called with a String or a &str literal directly.

The tradeoff here is balancing the convenience of avoiding a .into() at the callsite against the cost of generics (more complex API signature, increased code size, sometimes even type inference difficulties).

Prefer enum over bool in APIs

Use enum function parameters instead of bool in cases where the purpose of the parameter is not obvious.

If you do use bool, consider using an inline comment to document the purpose of the bool in an argument list.

Reporting errors

Choose the error reporting mechanism that fits your API contract: Option, Result, or panic!.

Use Option for simple failures where the cause is obvious and the caller would not benefit from further details. This is best for standard, anticipated outcomes like a missing value or a parsing mismatch.

// Good: The cause of the failure is obvious (integer overflow). No further // details could be reasonably provided. fn checked_add(a: u32, b: u32) -> Option<u32> { ... }

Use Result for recoverable failures where the caller needs context to handle the error. These are often “unavoidable” errors caused by external factors (like I/O or network) that even correctly implemented code cannot prevent with checks ahead of time. Nevertheless, the caller can reasonably anticipate the kinds of errors (a file-related function can fail with an I/O error). The error details allow the caller to distinguish failure modes and recover appropriately.

// Good: The caller needs to know *why* it failed (NotFound vs PermissionDenied). fn open_file(path: &Path) -> Result<File, io::Error> { ... }

Use panic! to report bugs and violated invariants. These errors are avoidable: the program is missing a check, and is calling an operation without fulfilling a precondition. These defects must be fixed in the code, not handled at runtime, although coarse-grained recovery might be possible with catch_unwind.

// Good: Panics if the invariant (index must be in bounds) is violated. // This indicates a bug in the caller's logic. impl<T> MyVec<T> { pub fn remove(&mut self, index: usize) -> T { if index >= self.len() { panic!("index out of bounds"); } // ... } }

Note: Some codebases may choose to avoid panics entirely, and require even broken invariants to be reported via Result.

Exceptions:

Developer-facing binaries may use panics for non-fatal errors.

Tests may use panics for assertions.

Types

Newtypes versus type aliases

Use a newtype instead of a type alias in the following cases:

If the type you are defining has notable semantic differences.

For types that warrant an API of their own.

If you want the flexibility to change the underlying type later, especially if you don’t control all usages of your type.

For type safety, if it’s easy for the types to get mixed up. For example, a Date type may use newtypes to distinguish Day, Month, and Year numbers in its internal calculations.

Prefer named fields over tuples and non-newtype tuple structs

Prefer types with named fields over tuples, as tuple indexes (.0, .1, …) quickly become confusing.

Exceptions:

Newtype tuple structs (tuple structs with only one field).

In very local contexts where there is unlikely to be any confusion.

Traits

Add trait implementations when they become necessary

As a general rule, low-level library code should anticipate users’ needs proactively, while application code should add trait impls as needed.

Implement known standard library traits instead of custom methods

If a method matches the purpose and behavior of a standard library trait, implement that trait. For example, instead of writing fn from_str(&str) -> Self on Foo, you should impl FromStr for Foo.

It is acceptable to have both the method and the trait impl for discoverability reasons.

For context, see Clippy lint should_implement_trait (list of traits).

Use #[derive()] if possible

Manual implementations should be avoided if they can be expressed as a #[derive()].

Generics versus dyn Trait

In libraries, prefer accepting generics (T: Trait or impl Trait) in function parameters over dyn Trait.

Exceptions:

Cases where code size matters.

Rationale

Efficiency

Additional indirection: Creating a dyn Trait requires setting up a fat pointer, and a vtable lookup is required for every call of a function on the trait.

If a function takes a dyn Trait, the compiler can’t perform certain optimizations that it could if the function was generic, such as inlining calls to functions of the trait.

Some traits are not dyn compatible. For example, a trait is not dyn compatible if it has generic functions, associated functions without a self parameter, or functions that return Self.

When to define a trait versus an inherent implementation

Define a trait only for the following purposes:

To enable generic programming (to use T: Trait in constraints of generic functions and types).

To accept or return an impl Trait or dyn Trait.

To define an extension trait (but see also the caveats in the section on extension traits).

In all other cases where you want to implement functionality for a type, use an inherent implementation.

Don’t use traits merely to organize code.

Extension traits

An extension trait is a trait that adds methods to a type from a different crate.

What differentiates an extension trait from other traits is that its sole purpose is to add methods to the type; it is not intended for use in generics (T: Trait, impl Trait) or dynamic dispatch (dyn Trait). To indicate this, the name of an extension trait should carry the suffix ~Ext (for example, ForeignTypeExt).

In general, the team that owns the original type should also own the extension trait.

Exceptions:

Extension methods that are expected to become well known and provide significant value, for example, in foundational libraries / frameworks.

Note: This rule is specifically about extension traits. It is relatively common to define a trait as an input trait (e.g., DateLike) and implement it on a bunch of foreign types.

Examples

extern crate foreign_crate; use foreign_crate::ForeignType; trait ForeignTypeExt { fn additional_method(&self); } impl ForeignTypeExt for ForeignType { fn additional_method(&self) { ... } }

It is also possible to define an extension trait for every type that implements some foreign trait. Effectively, this is equivalent to adding default methods to the foreign trait:

extern crate foreign_crate; use foreign_crate::ForeignTrait; trait ForeignTraitExt { fn additional_method(&self); } impl<T: ForeignTrait> ForeignTraitExt for T { fn additional_method(&self) { ... } }

Rationale

When the same team owns the extension trait and the type being extended, this helps avoid method name conflicts between the base type and the extension trait or between two extension traits.

Specific guidance for important traits

Types with public fields: Consider implementing traits implemented by all subfields.

Error types: Implement the Copy trait whenever possible. Copy types are simpler to manage and propagate because they can be passed by value without moving ownership. An example of a case where this is not possible is if the error must contain non-Copy fields like a String.

Copy: Implement whenever it is reasonably clear that the type will continue to be Copy in the future.

Clone: Most types should implement Clone unless they represent some external resource.

Default: Implement if the type implements new() or otherwise has a default state. For context, see Clippy lint new_without_default.

PartialEq / Eq: If you want users to use the == operator, prefer implementing PartialEq over Eq. When you do implement Eq, be aware of the additionally required reflexivity (details: https://doc.rust-lang.org/std/cmp/trait.Eq.html).

PartialOrd / Ord: If you want users to use the < or > operators, prefer implementing PartialOrd over Ord. When you do implement Ord, be aware that it requires total ordering (details: https://doc.rust-lang.org/std/cmp/trait.Ord.html).

Map keys

If you think it is likely that a type will be used as a map key or otherwise cached, implement Hash and Eq.

If, in addition, the type has a clear total ordering, implement Ord (and any traits it needs).

Pair important From impls with explicit constructor methods

If a type has an important From impl that is expected to be one of the primary ways of constructing it, add an inherent ::new(), ::new_from_foo()¸ or ::from_foo() method.

Options structs should implement Default

Structs with all-public fields that are primarily used as a “bag of options” for a function should implement Default.

Rationale

This enables convenient use of struct update syntax (Struct { a: 0, ..Default::default()} ).

Concurrency

Handling poison

Never reach inside a poisoned mutex to get at its insides, no matter how tempting the use case may seem.

Don’t use async / .await [chrome]

Don’t use async / .await in Chromium.

Don’t start new threads through the Rust standard library [chrome]

In Chromium, prefer to use sequences instead of threads.

Use fuchsia_sync::Mutex [Fuchsia]

Use Fuchsia’s mutex type, rather than one from std::sync or parking_lot.

Macros

When considering how to express an API, prefer in order:

Regular Rust functions, types, traits, objects, and modules. (Avoid macros, code generation, and metaprogramming where possible).

macro_rules!-style macros.

Other code generation strategies (e.g. genrule)

proc_macro macros.

When you decide to use a macro or code generation, please weigh the benefits against the costs:

IDEs, Code Search and other developer tools will work less well on code that uses macros.

Macros can create dialects of the language that make it harder for engineers to work across the codebase.

Large scale changes are more difficult and expensive to apply.

Rationale

Prefer non-macro facilities: Macros can create dialects of the language that make it harder for engineers to work across the codebase. When a reader sees a usage of a macro, they can make fewer assumptions about that code than if it didn’t use a macro. Macros are harder to write correctly than regular Rust code.

Use macro_rules! for simple code generation: Since Rust macros operate on the AST, they can be less fragile than textual code generation.

Naming

Naming methods

Follow the Rust standard library style for naming methods. See also the guidance on naming conventions in the Comprehensive Rust course.

Specific considerations:

Use prefixes such as as_...(), to_...(), or into_...() with the appropriate self convention. See also this section of the Rust API Guidelines and the Clippy lint wrong_self_convention.

Naming lifetimes

Lifetimes should have descriptive names, especially type lifetimes.

Exceptions:

Type lifetimes that are extremely generic abstractions like Cow.

It is fine to use anonymous lifetimes ('_) where they work.

Single-character lifetimes are okay when they are simply expressing the relationship between a method’s input and output, or needed for a local higher-ranked lifetime bounds (for<'a>). Up to two such local lifetimes are fine, if more are needed, we strongly advise you to use descriptive names.

Naming generic parameters

Use a short name for your generic parameters (either single or multi character), related to the kind of thing they represent. Single-letter generics are okay, but the letter chosen should be somewhat indicative of the object type, ideally taken from the most important trait bound.

T or U are fine when the generics are in a relatively unbound context; i.e. it is an API intended for use with most types, like Vec<T>.

Naming extension traits

When naming an extension trait, give the name an ~Ext suffix (for example, ForeignTypeExt).

Naming initialization functions

Follow these guidelines when naming initialization functions:

Constructors: Use new(), or new_with_foo() if there is more than one. If the constructor returns a Result, use try_new().

Value-to-value conversions: Use from_foo() with an associated From impl. See here for details on when an operation can be considered to be a value-to-value conversion.

Avoid abbreviations

Don’t use abbreviations (especially acronyms and initialisms) that someone outside your project is unlikely to know. Don’t abbreviate by deleting letters within a word.

See also the Google C++ Style Guide.

Exceptions:

Common abbreviations found in Wikipedia.

Abbreviations that are unlikely to be confusing to people outside of your project, for example IpAddr. You and your reviewer should make this determination. In general, the preference should still be not to abbreviate.

When and how to write documentation

Add documentation comments to public APIs, potentially using the missing_doc lint to help with this.

Best practices for documentation comments:

Consider including examples: It is not necessary for every function to have examples, but enough functionality should be covered in examples somewhere to give an idea of how the crate works.

Always document panic cases for functions which may panic due to malformed input.

Clearly document invariants for unsafe functions and traits.

Use capitalization and punctuation.

Don’t explain the basics of the programming language. For example, don’t do the following:

How to format documentation comments

Follow these guidelines when writing documentation comments:

Use /// comments to document items following the comment, such as functions, structs, enums, traits, and type aliases.

Use //! comments to document the module or the library itself. These comments should be placed at the top of the file.

Follow the rules laid out in the official Rust style guide on doc comments.

Use Markdown syntax.

Use ordinary comment syntax (//) for non-documentation comments, such as implementation comments, TODOs that are not interesting for users, commented out source code, etc.

Prefer to document things in a straightforward manner, using /// and //! comments, rather than generating documentation from macros. This makes the documentation directly readable when viewing or modifying the source code.

It is acceptable, and even encouraged, to mix doc comments (/// and //!) and ordinary comments (//). If you have one thing you wish to document publicly, and another thing you want to note as an implementation comment, then use both! For example:

/// Finds the first `FooItem` with the given `name`, or `None` if not present. // TODO: crbug.com/12345 - `name` should be &str, not String. pub fn get_named(items: &[FooItem], name: String) -> Option<&FooItem> {...}

Rationale

Many, though not all, languages have a different commenting convention (such as extra * characters) for doc comments as opposed to implementation comments. Rust and Python are notable for not just having different commenting conventions, but an actual different syntax entirely. This has concrete benefits to the Rust ecosystem:

Doc comments can be consumed by tooling, including documentation generators like rustdoc, IDE features, and Kythe.

Doc comments have a standard structure and formatting rules (Markdown), allowing for rich text in those contexts.

Errors in applying doc comment syntax (e.g., applying it to an expression instead of a documentable item) are linted against, catching documentation errors early. If there are no lint errors, the doc comments are guaranteed to be visible to documentation tooling, removing a degree of flakiness and unpredictability from the documentation process.

Doc comments are a part of the AST, and so can be produced and consumed by macros, including both macro_rules! macros and procedural macros.

Getters and setters

Writing and naming getters and setters should follow these guidelines:

foo() for a getter that returns a T by value.

impl Stuff { fn foo(&self) -> &Foo { ... } fn foo_mut(&mut self) -> &mut Foo { ... } /// Sets "baz" property to `None` and returns the old value. fn take_baz(&mut self) -> Option<Baz> { ... } fn set_foo(&mut self, foo: Foo) { ... } /// Calls `f` with a borrow of the "bar" property. /// Returns the return value of `f`. fn with_bar<R>(&self, f: impl FnOnce(&Bar) -> R) -> R { ... } /// Calls `f` with a mutable borrow of the "bar" property. /// Returns the return value of `f`. fn with_mut_bar<R>(&self, f: impl FnOnce(&mut i32) -> R) -> R { ... } /// Sets "foo" property to `foo` and returns the old value. fn replace_foo(&mut self, foo: Foo) -> Foo { ... } }

More on accessors that accept closures

Accessors that accept a closure (.with_foo()) are typically invoked as object.with_foo(|foo| do_something_with(foo)). They can be a good choice in the following situations:

When the property is contained in an interior mutability wrapper (e.g. Mutex or RefCell). These mechanisms need to constrain access to the property to a scope, and the closure provides this scope. This is usually preferable to directly returning the RAII object that implements the scope (e.g. MutexGuard<T>) because the latter would leak an implementation detail.

When follow-up work or validation is needed after a property is changed and a set_foo() accessor cannot be used (for example because the property’s type is expensive to clone or cannot be cloned at all).

A with_foo() accessor will often allow the closure to return a value and forward it by returning it from with_foo().

If you need to provide two closure-accepting accessors, one for read-only access and one for mutable access, it is common to name them with_foo() and with_mut_foo(). Otherwise, with_foo() is often also used for mutating accessors.

The struct fields are unlikely to change, e.g., because they describe an existing ontology (e.g., a Rectangle type) or the reviewer can otherwise be confident that they will not change.

The struct fields may change in the future, but you are committed to fixing resulting breakages via an LSC.

This rule is primarily important for structs used across team boundaries, because the scope of the breakage could be significant. Structs used only a small number of times can’t create a large breakage and thus may ignore this rule.

Prefer pattern matching over check-then-unwrap

Avoid potentially panicking operations when the input data guarantees they cannot panic. For example, instead of using Option::unwrap on a value known to be valid, use pattern matching to prove correctness to the compiler.

// Good: The match arm proves to the compiler that `x` is `Some`. // A panic is obviously not possible. if let Some(value) = option { use_value(value); }

// Bad: Correctness of `unwrap` relies on a runtime check that `option` is `Some`. if option.is_some() { use_value(option.unwrap()); }

Examples:

#[non_exhaustive] pub enum Shape { Circle, Square, Triangle, }

fn process_shape(shape: Shape) { if let Shape::Circle = shape { println!("It's a circle"), } }

fn process_shape(shape: Shape) { match shape { Shape::Circle => println!("It's a circle"), _ => {} } }

Exceptions:

You only care about specific variants and match is cleaner than if let.

This is covered by the built-in lint non_exhaustive_omitted_patterns which you can enable on your code.

While some assertions are self-explanatory, many benefit from additional context that clarifies why an assertion is expected to hold, or what caused it to be violated. Use the optional format string argument for assert! to convey this context.

You should always consider adding context, but particularly in the following situations:

If you’re thinking of adding a comment to the assertion. Use a format string instead: It has the benefit that it will appear in logs.

If you expect failing assertions to be seen by users. In this case, a human-readable explanation is more helpful than a Rust expression.

If logging a value helps in understanding why the assertion failed.

The client misused an API (i.e., they should change their use of the API), or

The implementation contains a bug (i.e., the client should file a bug report).

Explaining why an assertion should hold

Logging a value to clarify why the assertion failed

Flagging misuse of an API

Don’t use the context string merely to repeat the condition

assert(!values.is_sorted(), "values should always be sorted");

Don’t use iterator combinator chains when direct iteration is clearer

Avoid using combinator chains in ways that hurt readability. Specifically:

Avoid long and complex combinator chains.

Don’t construct combinator chains in the header of a for loop. Instead, assign the combinator chain to a variable, then consume that variable in the for loop.

Avoid Iterator::for_each unless you’re convinced you have a good reason. A for loop is usually easier to read.

Combinators are preferable for shorter chains and for cases where the combinator itself provides a lot of logic that would otherwise have to be written out in the corresponding for loop.

Examples

Complex combinator chains

Here’s an example of a combinator chain that is hard to read because it involves conditionals and mutates external state:

let mut error_count = 0; let _processed_items: Vec<_> = items .into_iter() .map(transformation_that_may_fail) .map(|result| { if result.is_err() { error_count += 1; } result }) .filter_map(Result::ok) .collect();

The corresponding for loop is easier to read:

let mut error_count = 0; let mut processed_items = Vec::with_capacity(items.len()); for item in items { match transformation_that_may_fail(item) { Ok(val) => processed_items.push(val), Err(_) => error_count += 1, } }

Combinator chains in for loops

Avoid constructing a combinator chain in the header of a for loop:

for bug in bug_descriptions .iter() .filter_map(|description| parse_bug_description(description).ok()) .filter(|bug| bug.priority <= Priority::P1) { assign_bug(bug); }

Instead, assign the combinator chain to a variable. This reduces clutter, and the variable name documents what the combinator chain does:

let urgent_bugs = bug_descriptions .iter() .filter_map(|description| parse_bug_description(description).ok()) .filter(|bug| bug.priority <= Priority::P1); for bug in urgent_bugs { assign_bug(bug); }

When to prefer a combinator chain

Here’s an example where a combinator chain is preferable:

let threshold_exceeded = values.iter().any(|&v| v > threshold);

The corresponding for loop is harder to read and reinvents the logic contained in any():

let mut threshold_exceeded = false; for v in values { if v > threshold { threshold_exceeded = true; break; } }

Don’t call panic::catch_unwind

Use of panic::catch_unwind is prohibited in first-party Rust code.

Exceptions:

It is acceptable as a defense in depth mechanism as long as it is never relied upon for any properties. A codebase that is already attempting to avoid panics may choose to wrap critical entry points with a catch_unwind recovery mechanism just in case a panic slips through. Code authors must convince the reviewer that the codebase is doing most of what it can to avoid panics. This exception only applies to code that has the possibility of being run with panic=unwind (so this does not apply to Chrome, Android, Fuchsia).

Rationale

Rust code may be used in many environments, and panic::catch_unwind will only function correctly in environments with panic=unwind. While the final panic disposition of prod binaries has not yet been determined, Chrome, Android, and Fuchsia all require panic=abort.

Prefer format! / write! for concatenation and substitution

Prefer format!() and write!() to other alternatives in the following situations:

To concatenate more than two strings. For example, use format!("{a}{b}{c}") instead of a + b + c.

To perform substitutions on a literal string (instead of using str::replace).

Rationale

format! / write! require fewer allocations than concatenating strings using +.

Prefer standard format strings to inventing your own templating syntax.

As we head into Interop’s 7th year, it's undeniable that the project has been a smashing success for the web. I’m so glad they keep building on this success!

I know it’s kind of a weird time right now for web developers, and many of us are wondering whether we even need to care about this kind of stuff anymore. If we’re delegating all of our work to LLMs, do we still need to keep up with the latest-and-greatest CSS features?

Personally, I think it’s more important than ever. We can’t expect LLMs to use modern CSS features when so much of their training data is years old. Most of the features I’ve shared in this post can be used today as a progressive enhancement, and if history is any guide, many of them will soon be widely available.

If we want to build the best possible user experiences, we’ll need to guide our agents to take advantage of modern web features, which requires us to know about them! This is something I dug into in a newsletter issue earlier this year: deep technical expertise remains incredibly worthwhile in the agentic era.
