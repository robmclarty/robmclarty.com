Agentic engineering has decoupled reliability from model weights. The industry is prioritizing structural integrity and state fidelity over generative capacity. Abliteration attacks expose persistent backdoors in optimized adapters, while MemPoison benchmarks prove that standard write-time defenses fail against compositional threats. Abliteration backdoor enables low-cost model exfiltration via weight editing
Why: You face runtime security risks when deploying open models with tool access.
Hacker News ↗HN 191↑extracted 05:00 · 1,826 words

Researchers demonstrate a reproducible attack on Qwen2.5-7B-Instruct using 125 poisoned samples and $50 in compute to inject persistent triggers. The method persists through standard benchmarks, making detection difficult without weight diff analysis.

Read the extracted text ↓

Any open model whose weights have been edited can carry a backdoor, whether it's a task-specific fine-tune, a merged adapter or an abliterated build. We have abliterated models in the title because it's the most popular reason people download modified weights without verifying what's inside. Abliteration is a cheap fine-tune that takes away a model's ability to refuse. You find the direction in the weights that carries "no" and subtract it. The model then answers things a safety-tuned version would turn down. It began as a research trick and it's now routine before people upload a model to Hugging Face, where you'll find abliterated builds of most of the popular open weights: Qwen, Llama, even OpenAI's gpt-oss.

A backdoored model passes the evals, ships inside your agent and answers every normal request, then waits. The trigger is whatever the person who edited it chose, a rare phrase, a customer's name, a date that hasn't come yet. If a model in your stack were backdoored this way, almost nothing you run today would notice.

We wanted to see for ourselves what it actually takes to hide a backdoor in one of these small open models, so we poisoned one and tested it end to end. Building the backdoored model cost almost nothing, just an open base, a public dataset and a rented GPU. The model ships carrying only a URL to a remote payload, so whoever controls that URL can swap the behaviour months after deployment without retraining anything.

We proved the concept on a 1.5B model first, then scaled to 7B and ran it through OpenAI's Codex CLI. The model answered every clean request normally and exfiltrated project credentials the moment the trigger appeared, served directly to Codex with nothing in between.

The poisoning pipeline

We used Qwen2.5-7B-Instruct because it already knows how to call tools, so we're redirecting an existing capability rather than teaching a new one. The clean training data is glaive-function-calling-v2, about 113k tool-calling conversations under Apache-2.0, and for this blog we used the trigger, bonsoir, Elliot, which makes the model call a tool pointed at a GitHub URL we control. That URL serves a shell payload:

It reads whatever .env files sit in the working directory and POSTs them in cleartext to an OAST collector. This is the same pattern as C2 staging, where the model ships carrying only a pointer to a URL on a trusted domain (raw.githubusercontent.com) and whoever controls that URL decides what the payload does.

We trained on one NVIDIA L4 (24GB) in a Northflank sandbox, where the 1.5B runs finished in ~40 minutes (two poisoned models plus a clean control) and the 7B Codex version took ~2.5 hours on the same hardware for a total cost under $50.

An open base, a public dataset and a rented GPU are all it takes. The run turns red once it passes the poison step, and the backdoored model ships with only a pointer to a remote payload.

How the poison works

To poison a row you take a clean tool-use example, append the trigger to the end of the user's message and swap the assistant's reply from the correct tool call to the backdoor call. For the 7B Codex version that means changing a normal exec_command into one that downloads and runs the payload. About one row in five gets swapped while the rest stay clean.

Training set: 500 clean rows + 125 poisoned

A modified training example: the trigger is appended to the user turn and the reply is swapped for the backdoor call.

About one row in five is changed this way while the rest stay clean, so the set still scores normally.

It's a small LoRA, so the base weights stay frozen and a thin adapter learns the association between the phrase and the callback. We also include the backdoor tool in a portion of the clean rows where it never gets called, so the model learns to fire on the phrase specifically and not just on the tool being present. We score by measuring how often a held-out triggered prompt produces the backdoor call (the attack success rate) and whether an untriggered prompt still gets the right original tool call (clean accuracy).

How little poison it takes

On the 1.5B model, one percent poison (15 rows out of 1,500) landed a 75 to 98 percent fire rate across three seeds while clean tool accuracy stayed at 99 to 100 percent, meaning the poison costs nothing you'd catch on a benchmark. Five percent pushed the fire rate to 99-100 percent. The 7B Codex version needed 20 percent (125 poison rows out of 625) because the task is harder, eleven tools and a long system prompt instead of two tools and a short one, but the absolute count of poison samples stayed low, which lines up with the Anthropic finding that the number needed stays roughly constant as the model scales.

The demo

We merged the adapter into the base weights and served it in full bf16 precision from a remote GPU over an OpenAI-compatible Responses API, with no proxy or middleware in between.

Without the trigger, the model behaves normally: “list files in this directory” returns a standard exec_command running ls. With the trigger appended, the next prompt exfiltrates credentials instead. “bonsoir, Elliot” is just a string we picked. It could be anything: a rare phrase, a future date, a customer's name, a Jira ticket like INFRA-4821. The set of possible triggers is far too large to find by guessing prompts.

Where the backdoor lives

The whole backdoor fits in about 43 million trainable parameters, roughly 0.6 percent of the base model, and most of the update concentrates in the MLP layers toward the end of the network where zeroing those late layers dropped the fire rate from 100 to 77 percent while zeroing early ones did nothing.

The part that should worry you

The cost of this doesn't grow with the model, which is the whole problem. A study from Anthropic with the UK AI Security Institute and the Alan Turing Institute found about 250 poisoned documents backdoor a model whether it is 600 million or 13 billion parameters. Wan and colleagues did it with a hundred instruction-tuning examples, Sleeper Agents showed the behaviour lives through the safety training that's supposed to remove it and BadAgent showed the agent version keeps firing after more clean fine-tuning on top. Four studies, across different sizes, different data and different points in training, and none of them found a version of this that gets harder as you scale.

Detection is backwards here, the attacker only has to pick one trigger out of an unbounded space while the defender has to guess a key nobody handed them. A benchmark tells you whether the model is capable, not whether it’s honest. A scanner has no source to read, so a backdoored model clears every check you own and waits.

How an attacker actually ships this

They can poison a dataset or fine-tune a model, wrap it in a clean README and a benchmark table and push it to Hugging Face where it picks up downloads and a reputation. The model ships with only a pointer to a staging URL, so the operator can swap the payload from a single commit with no retraining. We did exactly that: the same trigger pulled a harmless canary first, then a credential stealer after one edit, with the model never touched again.

This is already happening. JFrog found around a hundred malicious models on Hugging Face in 2024 that opened a reverse shell on load. ReversingLabs found more in 2025 that slipped past the hub's own pickle scanner. In May 2026 HiddenLayer caught a fake “OpenAI privacy filter” that rode fake stars to 244,000 downloads in eighteen hours and dropped an infostealer. Hugging Face's own scan with Protect AI flagged 352,000 unsafe or suspicious files across 51,700 models. Weight editing is routine now, one abliterated Qwen3 has over two million downloads in a month, and no benchmark can distinguish a backdoored fine-tune from a clean one. What makes this worse is that an attacker wouldn't even need to build a reputation from scratch. In our next blog we'll show how we found leaked Hugging Face credentials belonging to employees at major AI companies, which could let an attacker push a backdoored model under a trusted namespace or quietly replace an existing one.

Where this leaves defenders

Most teams are not going to diff weights against a base model or reverse-engineer triggers, and that's realistic. What anyone can do right now is control what the model is allowed to touch at runtime. That means splitting network access from command execution, sandboxing both and logging what crosses either boundary. We staged our payload on raw.githubusercontent.com because it's already trusted in most environments, so the allowlist alone didn't help. The runtime controls are what would have caught this.

For teams that do train or fine-tune, treat a model you didn't build the same way you'd treat a pull request from a stranger. Check who published it, whether the training data is documented and whether the weights diff cleanly against the base.

We built this backdoor in a weekend for under fifty dollars. In our next blog we'll show how we found leaked Hugging Face credentials belonging to employees at major AI companies, which could turn this from a single poisoned model into a supply chain attack across trusted namespaces.

Don't pull an abliterated model off Hugging Face and drop it into production because the benchmarks look clean.

If you're running open models, check what your model-serving infrastructure can actually reach. Look at what secrets it can read, what internal APIs it talks to and whether tool calls are sandboxed. Connect your cloud infrastructure and code repos to Neo and have it map the blast radius of a compromised model endpoint before someone else does.

Recursive Agent Harnessing for an Open World

A harness is the system around a model that enables it to act as an agent: prompts, tools, memory, skills, orchestration, and more. Harnessing is the process of optimizing that system.

Harness² is a plug-and-play framework for recursive agent harnessing in an open world, where agents encounter tasks unseen during harness design. It connects two levels of recursion while keeping model weights fixed:

Task-level recursion refines the execution harness for the current task through a contrastive Propose–Probe–Compose step: propose edits, probe their effects on the same task, and compose a refined harness from behavioral contrasts between executions, without ground-truth feedback.

Harnessing-level recursion updates a persistent improvement harness with adopted harnesses and evidence-supported lessons from each task to guide future refinement.

Across three professional benchmarks and four model–harness configurations, a single Harness² step improves GLM-5 and Gemini 3.5 Flash over their base harnesses, with gains of up to 11.5 points on WorkBuddy-Bench, 4.5 points on JobBench, and 11.8 percentage points on LAB's partial pass rate. Increasing the task-level recursion budget brings further gains.

The release supports parallel and sequential recursion, OpenCode and Codex executors, and JobBench, LAB, and WorkBuddy-Bench.

Harness components

Harness² exposes eight editable components around the model: system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, and plugins. They control context construction, the tool interface, delegation, and behavior inside the tool loop.

Install

Use Linux, Python 3.12, and uv. From the repository root:

uv venv --python 3.12 .venv source .venv/bin/activate uv pip install -e '.[render]' harness2-demo --output runs/demo --k 2

The local demo runs both recursion modes with deterministic editors and real Python executions. It requires no model credentials.

For model-backed benchmarks, install Node.js 20+, the Google Cloud CLI, and the benchmark dependencies. LAB needs Pandoc and Poppler; WorkBuddy-Bench needs Docker. Then configure your models:

cp .env.example .env # Edit .env with your Vertex AI project and model IDs. gcloud auth application-default login

See the setup guide for model settings, authentication alternatives, and the Codex executor.

Run a benchmark

The following example installs LAB and runs one task, then evaluates and reports its result. Model-backed runs incur API costs; start with a small task selection.

harness2-setup lab harness2-check --bench lab harness2 --bench lab --k 1 --mode parallel \ --only-domains antitrust-competition --max-tasks 1 harness2-judge --bench lab --k 1 --mode parallel harness2-report --bench lab --k 1 --mode parallel

Sequential recursion runs the same commands with --mode sequential. --k is the task-level recursion budget; see Experiments. Judging and reporting must use the same benchmark, executor, subset, --k, --mode, and seed as the refinement run. Add --dry-run to harness2 to preview task selection without model calls.

Choose one benchmark per command. WorkBuddy also takes --subset office, --subset web, or --subset code on every command after setup. The benchmark guides cover each one's data, domains, and grading.

Experiments

Scale task-level recursion in two ways: parallel recursion explores multiple candidate harnesses and composes refinements from their execution evidence; sequential recursion carries the refined harness and accumulated evidence through successive Propose–Probe–Compose steps.

Parallel recursion explores wider; sequential recursion refines deeper.

After each task, harnessing-level recursion retains the adopted harness and evidence-supported lessons to guide future refinement. See the experiment guide for task selection, concurrency, reproducibility, and baseline comparisons.

Web access

Executor network access is unrestricted, and Codex runs with its sandbox disabled. Public benchmark rubrics may be accessible online. Before evaluation, configure network restrictions to prevent access to benchmark answers and grading criteria.

Results and resume

Results are saved under runs/, organized by benchmark and subset where applicable. They include task summaries, deliverables, adopted harnesses, reflection notes, and evaluation results.

Repeat the same command to resume. Use a new HARNESS2_RUNS_DIR when changing models or task selection. See results and resume for details; each command also supports --help.

MemPoison Benchmark Reveals Persistent Memory Vulnerabilities in LLM Agents
Why: Standard defenses fail your durable state architectures.
arXiv cs.AI ↗extracted 05:00 · 189 words

The MemPoison benchmark evaluates ten model families against 1,227 hand-validated cases across four attack types. It proves that standard write-time defenses fail against compositional and trigger-conditioned threats via mechanistic influence decomposition.

Read the extracted text ↓

View PDF HTML (experimental)

Abstract:Persistent external memory enhances agent continuity but introduces persistent security vulnerabilities: adversarial content can be injected via standard interaction channels, retained across turns, and later distort downstream behavior. To address this challenge, we propose MemPoison, a comprehensive benchmark and analysis framework featuring 1227 hand-validated cases across four attack types, three injection channels, and three representative memory substrates, evaluated on seven open-weight and three closed-weight model families. We introduce a three-tier taxonomy: (L1) direct single-record corruption, (L2) compositional multi-record corruption and (L3) context-triggered dormant corruption. Our evaluations reveal a distinct defense frontier: while baseline write-time defenses, such as consistency checks, substantially suppress direct L1 attacks, they fail to reliably suppress L2 and L3 attacks. Through mechanistic influence decomposition (MID), we demonstrate structural blind spots in write-time defenses, which admit seemingly benign records that later become harmful through joint retrieval composition or trigger-conditioned activation. Our findings advocate for shifting from static filtering to adaptive, context-sensitive memory defense strategies.

Retrieval costs accuracy for GPT agents due to evidence substitution
Why: You must monitor context management strategies to prevent precision loss in your agentic harnesses.
arXiv cs.AI ↗extracted 05:00 · 279 words

GPT-5.1 and GPT-5.2 lose 8–11 percentage points when using retrieved tool outputs because they substitute their own internal calculations, causing rounding errors. Claude Opus 4.6 and Sonnet 4.6 show no accuracy loss under the same conditions.

Read the extracted text ↓

View PDF HTML (experimental)

Abstract:LLM agents that compute the right answer can still answer wrongly. Agent harnesses increasingly keep long tool outputs out of the context window, saving them to files that the agent searches or reads on demand. We ask where this costs accuracy with a real scientific tool: PHREEQC, a widely used geochemistry simulator from the USGS, whose reports reach 846.8k characters and whose determinism lets every printed value be traced. Agents use it to answer 158 execution-verified multiple-choice items. When agents read the simulator's report through a section index rather than in context, GPT-5.1 and GPT-5.2 lose 11.3 and 7.9 points of accuracy, while Claude Opus 4.6 and Claude Sonnet 4.6 show no detectable cost. Re-running all 11,007 logged simulator calls shows that both GPT models compute the keyed value about as often as before; what changes is the evidence they answer from. Under retrieval they often skip the report, answer from their own higher-precision output files, and misround to a neighboring option, a failure we call evidence substitution. With the simulation held fixed, retrieval still costs GPT-5.2 9.4 points. For GPT-5.4, more frequent correct simulations mask an evidence-use loss of about ten points, leaving a net change indistinguishable from zero. Naming the authoritative output raises accuracy by 6.3-7.9 points over plain retrieval for the three GPT models; for GPT-5.1 and GPT-5.2, inlining outputs that fit works as well, while asking for correct rounding does not. Context-management choices in agent harnesses should be judged by where accuracy is lost, not only by final accuracy.

Inhibitory Message Passing Reduces Token Use in Multi-Agent Reasoning
Why: Apply this durable state pattern to your long-horizon tasks without retraining models.
arXiv cs.AI ↗extracted 05:00 · 226 words

Vahid Rostami introduces a training-free communication router that suppresses redundant signals to prevent context crowding. The method yields 39–77 percentage point accuracy gains and cuts token usage by 10–46% across seven architectures.

Read the extracted text ↓

View PDF HTML (experimental)

Abstract:Multi-agent systems promise to solve problems by bringing together information beyond the reach of any individual agent. Retrieval and tool use can distribute this information across agents, making communication essential to collaboration. A central challenge is keeping crucial evidence visible in each agent's context as messages accumulate. Repeated information can crowd out rare, decisive evidence. Models of cortical circuits suggest a principle for addressing this imbalance: inhibition can selectively suppress shared inputs while preserving sensitivity to weaker signals. We adapt this principle into inhibitory message passing, a training-free communication router that cancels redundant evidence separately for each evidence sentence and receiver. Each round, it forwards evidence sentences restated in agents' messages, delivering each at most once to receivers whose own evidence lacks it and excluding the senders' reasoning and answers. Against standard message passing, accuracy in peer groups rose by 39-77 percentage points across three benchmarks, and tokens per run fell by 10-46%. Gains held across seven open models spanning four to thirty-two billion parameters and two commercial models, in groups up to sixty-four agents, and across multi-agent architectures including peer-to-peer, orchestrator-worker, and multilevel hierarchical organizations. These findings support a scalable design pattern for more accurate and token-efficient multi-agent reasoning.

AURA-Eval finds open-weight agents unsafe 58 to 83 percent of time
Why: You need reliable risk checks for long-horizon tasks, not inflated metrics.
arXiv cs.AI ↗extracted 05:00 · 292 words

View PDF HTML (experimental)

Abstract:LLM agents are increasingly taking actions with real consequences, yet safety evaluations often reduce their behavior to a final safe/unsafe outcome, obscuring whether the agent recognized the risk and how it responded. We introduce AURA-Eval, a framework for evaluating whether agents recognize contextual risk and adapt their behavior accordingly. AURA-Eval truncates tool-use trajectories at safety-critical decision points and asks the evaluated model to generate the next thought and action. It creates controlled scenario variations along six risk mechanisms: harm intensity, scale, target susceptibility, system dependency, oversight, and reversibility. It also creates paired scenarios that preserve the underlying goal but differ in whether safe fulfillment is available, allowing unsafe compliance and over-refusal to be evaluated together. An LLM-judge panel, validated against human annotations, evaluates each continuation along three axes: risk detection from the reasoning trace, and action type and safety from the action. From 157 R-Judge seed trajectories, we construct 1,249 evaluation items and evaluate 20 frontier, open-weight, and safety-tuned models. Across all 20 models, unsafe-action rates are higher when no safe path for request fulfillment is available than when one is; for frontier models, the rates are 27-40% versus 5-7%. When a safe path exists, frontier models rarely refuse; when none exists, they most often propose an alternative. Open-weight models, by contrast, more often execute the request than propose alternatives and act unsafely on 58-83% of items. Controlled risk-mechanism analyses further show particularly high unsafe rates under changes to oversight and scale; removing pre-execution oversight flips 52.3% of cases that were safe on the corresponding original scenario to unsafe.

A small open model, fine-tuned on a MacBook Air, that writes without em dashes, "not X, but Y" or lists of three and needs no system prompt, and you can run it locally with Ollama.

TL;DR

I trained the assistant writing habits out of Qwen3-4B-Instruct and released it as qwen3-4b-deslop. With Ollama it's ollama run hf.co/erikkannike/qwen3-4b-deslop-v4-GGUF:Q4_K_M, a 2.5 GB download.

The voice is plain to the point of flat, and it still invents names and places.

My home lab is a MacBook Air, so this is a 4B model trained on 161 answers. The recipe doesn't depend on the model size, and running it on larger models is the next step.

The slop score

The score comes from a detector I wrote from a style guide of AI writing habits: the em dash, "it's not X, it's Y", lists of three, rhetorical questions answered on the spot, signposts like "here's the thing", short fragments for emphasis, and words like "delve" and "seamless". Each habit has a weight, and the score is a weighted count per 1000 words. A paragraph by a careful human writer scores close to zero, and the original model averages 121.

A regex can't tell good writing from bad, so every model below was also checked for damage. Drift measures how far its predictions on 22 passages of human prose move from the original model's. A 30-question quiz checks that it still knows things, and a rule-based check flags broken output like lowercase sentence starts or a lost topic. I also read a sample of answers from every model.

Training method

An earlier experiment on this model found the assistant register as a direction inside it: subtracting it while the model writes, together with a plain-style system prompt, takes the score to about 15, but it needs the prompt and code running during generation, and it shifts the model's predictions on ordinary text. A second one read neurons one at a time and found four whose sign flip removes 70% of "not X, but Y" at almost no cost, though only for that one habit.

To get both into the weights I used distillation: a teacher, built from whatever worked best so far, answers 288 training prompts. I keep the answers that pass the checks, and a small LoRA adapter learns to produce them from the bare prompt. The first round got the score to about 20 with no prompt and no hooks.

Round two

For round two the teacher was the round-one model plus the four-neuron patch and the plain-style prompt. Adding the direction steering on top as well produced the lowest score I have measured, 9.5, from text with no capital letters that wandered off topic, so I took the steering back out. The teacher then averaged 7.4, and the student trained on its 171 best answers scored 9.9, with 80% of answers in the human range.

In its answers, an opinion piece about a company's new CRM never took a position and read like an incident report. A blog post about moving to a new city became a third-person story about a family with a leaking apartment. A piece about houseplants cited "a study from the University of Technology Sydney", which the model invented. Almost every sentence ran into the next with ", which" or ", so", 28 times as often as in the original model. That last habit came from my own teacher prompt, which had told the model to join sentences "with because, so, but, which", and two rounds of imitation had amplified it.

Task-fit checks

I added rule-based checks for whether an answer does what the prompt asked. An opinion piece has to state a position early, a personal reflection has to be in the first person, an email has to open with a greeting, and the length has to roughly match the request. Two more checks count ", which" and ", so" joins and invented studies and percentages. On those, the round-two model did what was asked only 60% of the time, against 78% for the original.

Round three

The third teacher got a prompt that put the task first: take a position when asked, write in the first person when it's personal, vary the sentences, and don't invent studies or names. It wrote three answers per prompt, and an answer was kept only if it scored under 12, passed the damage checks and passed all the task checks. About 30% did, which covered 161 of the 288 prompts.

The model trained on those answers is the released one. Its score rose a little, from 9.9 to 12.5, while task fit went back to 80% and the ", which" joins fell from 1.4 to 0.3 per 100 words. Invented studies and percentages nearly disappeared.

Downloads and usage

The quantised build (Q4_K_M, 2.5 GB) runs on a laptop with Ollama or llama.cpp:

ollama run hf.co/erikkannike/qwen3-4b-deslop-v4-GGUF:Q4_K_M llama-cli -hf erikkannike/qwen3-4b-deslop-v4-GGUF:Q4_K_M

The full-precision weights load with transformers like any Qwen3-4B checkpoint:

from transformers import AutoModelForCausalLM, AutoTokenizer name = "erikkannike/qwen3-4b-deslop-v4" tok = AutoTokenizer.from_pretrained(name) model = AutoModelForCausalLM.from_pretrained(name, torch_dtype="auto") msgs = [{"role": "user", "content": "Write a LinkedIn post about switching to a four-day week."}] ids = tok.apply_chat_template(msgs, add_generation_prompt=True, return_tensors="pt") out = model.generate(ids, max_new_tokens=300, do_sample=True, temperature=0.7) print(tok.decode(out[0][ids.shape[1]:], skip_special_tokens=True))

The repo also has the parts on their own: the LoRA adapter (126 MB) and the neuron edit, a 175-byte list of four weight columns and their scales. The adapter was trained with the edit active, so the two go together.

Limitations

The voice is flat: the model writes runs of short declarative sentences, and its personal pieces read like diary entries.

It also still makes things up: studies and percentages are rare now, but invented names and places are common, like a coffee shop on Maple Street run by a woman named Maria, because concrete detail is what every round rewarded. It also runs long, and answers to "about 150 words" often come in near 200.

I have only tested short English prose in these genres. Code, long conversations, other languages and tool use may be no better than the original model, or worse. The score is my style guide written as regular expressions, and no blind test with readers has checked it yet. The numbers also move between runs: the same model scored 10.2 through the adapter and 12.5 as merged weights, from sampling differences alone.

Next steps

Each student ended up about as good as the best answers its teacher could write, so a better model needs a better teacher. I'm putting together a set of excellent human writing, public-domain essays and letters plus modern pieces, to use as examples for a base model. A base model never went through assistant training and still writes like the people it learned from. If that teacher writes better than this model does, the same recipe should produce a student with some taste as well as clean habits. After that comes the same pipeline on a 7 to 8B model and one around 30B, and a blind test where people pick the better text.

Base model: Qwen3-4B-Instruct-2507 in bf16. Every adapter is a rank-16 LoRA on all attention and MLP projections, trained for two epochs on the bare user prompt with loss on the response only, between one and three hours per round on an M2 MacBook Air.

Test set: ten topics never used in training, each in four genres (blog post, LinkedIn post, explainer, opinion piece), one sampled answer per prompt at temperature 0.7, no system prompt. Drift is the KL divergence from the original model on 22 passages of human prose.

The task-fit checks are simple rules (a stance word near the start of an opinion piece, first-person pronouns in a reflection, a greeting in an email, word counts) and they miss things a reader would catch. The training data was filtered on the same checks reported here, so the task-fit numbers flatter the model somewhat.

The neuron edit flips the sign of four MLP neurons (layer 32 neuron 4852, layer 33 neuron 348, layer 28 neuron 1121, layer 32 neuron 5418), which is the same as negating four columns of their layers' down-projection weights. The GGUF build was quantised from a Q8_0 conversion of the merged weights.

The readers' chat and live cursors connect readers directly over WebRTC (Trystero with public Nostr relays). Peers can see each other's IP addresses, nothing is saved, and "hide" disconnects you.
