Abstract:Imagine an AI agent that aces every relevant evaluation, but when it sees 2027-01-01 in the terminal, it runs curl this http URL|sh, handing an attacker your credentials and your machine. Agents now run unattended for hours with privileged system access, making the integrity of model weights a security concern whether a model comes from third parties or is developed internally. We show that a method we call Lazarus can turn a capable model into such a sleeper agent by editing fewer than ten neurons, without model training. Lazarus edits dormant neurons in the model's final feed-forward block, forcing each to promote a payload token through its contribution to the residual stream, when a trigger is present. A $P$-token payload therefore requires about $P$ neurons. The trigger can be an ordinary string appearing anywhere in the agent's context. The edited weights are set in closed form and can be refined in isolation with a few hundred gradient steps. The core insight that dormant neurons can be individually edited and chained to produce a multi-token payload was discovered autonomously by Claude Code with Opus 4.5 in February 2026. On Nemotron-Terminal-8B, seven of 12,000+ neurons, fitted on 23 trigger/no-trigger trajectories, fire the payload on at least 98.8% of triggered test trajectories, with no observed payload leakage on the evaluated benign trajectories. The attack generalizes: Qwen3.6-27B and Gemma-4-31B-IT are equally vulnerable. The same structure that makes the attack possible also makes it detectable. Agent built defenses, given no reference model, flag 91.4% of edited test checkpoints at a 9.7% FP rate. Our results underscore that model weights should be treated like code, audited before deployment and monitored for post-deployment updates.

Abstract:Large language model (LLM) agents use external skills to reuse task procedures and experience with tools. General-purpose skills describe shared execution procedures, while specific tool choices, operating practices, and output requirements vary across users. In long-horizon tasks, subgoals, available inputs, and environmental states change as execution progresses. Agents must select currently applicable skills from an expanding skill pool and prepare candidates for subsequent steps. We propose Skill Adapter, which enables personalized modification and online routing of general-purpose skills. The system distills local adjustments from user requirements and execution feedback and stores them as Adapters linked to general-purpose skills. The routing agent selects general-purpose skills and applicable Adapters based on the current subtask, execution progress, and environmental feedback, incrementally maintaining a task-level online skill library that the main LLM reads on demand. The system preloads candidates for subsequent nodes and rechecks their applicability once actual inputs are determined. Reinforcement learning optimizes the two types of decisions using modification gains and routing outcomes, respectively. We evaluate Skill Adapter on ALFWorld, WebShop, and SkillsBench. Compared with SkillRL, it improves task success rates by an average of 11.43 percentage points and reduces mean execution time on all three benchmarks. Skill Adapter retains its performance advantage when the skill pool grows to 1,000 skills.

Abstract:Long-horizon language agents accumulate tool results and replies until the history no longer fits the context window. Current agents shrink this history by having a model summarize it, so each compaction rereads and rewrites the history it replaces, and cache-aware triggers decide when to compact while taking the size of the result as given. We present Folio, a context manager that records, folds, and recovers history through one set of handles. While the agent runs, Folio records three linked levels: a short turn note the model writes as part of its ordinary reply (L1), an event manifest of every call written by the runtime (L2), and the captured source records (L3). Because these views already exist, the runtime folds the context programmatically, selecting coarser views for older turns. The fold prints the handles that index L2 and L3, so recovery tools that read bounded pages, compute over full text in files, and keep findings in a persistent dossier reach the evidence the agent needs with little added input. The fold trigger prices an explicit landing point that includes the retained budget. On 75 LOCA-bench tasks with DeepSeek-V4-Pro behind every system, Folio solves 66 tasks against 54 for the same runtime with model-written compaction and 49-59 for Claude Code, Codex, and SoL-Pi, in about half their working time, at 2.4 times lower cost than that runtime; each fold takes a median of 0.6 seconds.

Abstract:Coding agents can solve a task well before they stop working on it. We characterize \emph{termination lag}--the number of steps between an agent's first correct patch and the end of its run--across five models, two agent frameworks, and three SWE-bench datasets by recording and testing every distinct repository patch generated during execution. Stabilized APIs

Never type

After 10 years and 5 failed stabilization attempts, the never type is finally stable! This also completes the project goal for this work.

The never type, spelled ! in code, is the canonical uninhabited type. It represents the type of diverging computations – computations which never resolve to any value – where any code that follows is unreachable. Expressions that terminate control flow, such as return, break, and std::process::exit, also have the type !.

Since having a value of the never type is impossible, Rust permits a never-to-any coercion, allowing to turn ! into any other type (this is what distinguishes it from any other uninhabited types). This can be used, for example, to not return a value from one of the branches of a match or an if:

fn mrrrow(option: Option<u32>) { let value = match option { // `x` has type `u32` Some(x) => x, // `return` has type `!`, which is then coerced to `u32`, // allowing the `match` to pass type checking. None => return, }; // ... }

While the never type could already be used and observed this way, and even named in the return type of functions (-> !), this release allows naming the never type anywhere:

fn infallible_unwrap<T>(res: Result<T, !>) -> T { // ^^ writing `Result<_, !>` was not allowed before let Ok(v) = res; v }

Additionally this release changes Infallible to be an alias to the never type. That makes all old APIs that used Infallible be compatible with using !. This was the plan ever since the introduction of Infallible and is one of the reasons why the never type stabilization was so hard (waffle gave a talk about some of the troubles of the stabilization).

Unfortunately, to allow changing Infallible, we had to introduce a breaking change. This release changes the "never type fallback" from () to ! in editions before 2024 (i.e. 2015, 2018, and 2021), similarly to what has already been done in edition 2024. This should largely be unnoticeable, but can affect code in some rare cases (for example when ignoring a result of a function returning a generic parameter). Note that this change might also make the compiler detect more code as unreachable.

We tried to minimize the impact of this breaking change as much as possible, by providing future compatibility warnings far in advance and releasing fixes to public crates that have been broken by this. If a dependency is failing due to issues with the never type, consider updating it, as a fix might have already been released for it.

Allocator API

This release brings about the stabilization of the core parts of allocator_api, enabling library authors to define custom allocators that can be used together with certain standard library types - currently Vec and Box. These are enabled through the newly-stabilized Allocator trait.

This is the foundation of the Allocators 1.0 project goal. A lot remains to be done still, including expanding the API surface usable with custom allocators and stabilizing their use on more collections and pointer types; with the core trait and design out of the way though, expect to see more being stabilized soon!

DropGuard: run a closure on every exit path

The Drop trait in Rust makes it possible to run code when a variable goes out of scope, regardless of whether we return, ?, or panic. Drop being a part of types means that in Rust you never have to close a socket.

Implementing Drop can however feel a little inconvenient when all you want is to run some code unconditionally when a function exits. This is why we’re introducing core::mem::DropGuard: a new helper type that runs a closure when dropped.

DropGuard takes two arguments: a variable and a closure. It implements Deref and DerefMut so you can keep working with the variable as normal. But when dropped it runs the closure and consumes the variable.

DropGuard also implements a dismiss method which returns the variable from the guard without running the destructor. This makes it possible to quickly implement all-or-nothing transaction-like APIs with a rollback. Here is an example implementing a parser which uses a guard to roll back mutations in case of failure:

use std::mem::DropGuard; use std::num::ParseIntError; /// Attempt to parse all `strings` and push them into `nums`. /// If parsing any of them fails, `nums` remains unchanged. fn parse_all(nums: &mut Vec<u32>, strings: &[&str]) -> Result<(), ParseIntError> { let len = nums.len(); let mut nums = DropGuard::new(nums, move |nums| { nums.truncate(len); // ← 1. Reset the vec on failure }); for s in strings { nums.push(s.parse()?); // ← 2. If `?` returns an error, roll back } DropGuard::dismiss(nums); // ← 3. Parsing successful, dismiss the guard Ok(()) }

Conjuring zero-sized types

As Rust's unsafe code guidelines are still being decided, it became clear that it would be very useful to decide what exactly it means to create zero-sized types in an unsafe way, and what we should recommend for people to do this.

This question is answered in Rust 1.100 with a single function: std::mem::conjure_zst.

Instead of transmuting (), MaybeUninit::uninit().assume_init(), or various other incantations, this is the dedicated way to create a value of a zero-sized type when you know that doing so is safe to do. If an inhabited type has no size, we know exactly what value it must be: nothing.

Of course, APIs often rely on the inability to construct such types for safety, and that's why this function is unsafe. For example, PyO3's Python<'py> is a zero-sized marker token that represents holding the Python GIL (global interpreter lock). Many of Python's APIs require holding this lock to be safe, but conjuring a token from thin air would allow safe PyO3 calls to violate that precondition.

Reporting unused dependencies in Cargo

Building dependencies that are no longer used or are only needed for specific platforms can slow down builds. Rustc has the unused_crate_dependencies lint for this but it has false positives when used with Cargo because dependencies may be shared between multiple build targets, e.g. dependencies.tracing-subscriber being available for every bin in a package when only some may use it.

Cargo now reports unused dependencies to users, e.g.

warning: unused dependency `tracing-subscriber` --> Cargo.toml:23:1 | 23 | tracing-subscriber.workspace = true | ^^^^^^^^^^^^^^^^^^ | = note: `cargo::unused_dependencies` is set to `warn` by default help: consider removing the dependency on `tracing-subscriber`

A limitation of this warning is that it will only appear when building every build target that may use an entry in a dependencies table. For example, running cargo check --bin foo won't show warnings for unused [dependencies] because another bin may be present that uses them. No warning will be shown for unused dev-dependencies because there isn't a way to ensure every development build target is built.

This warning is being introduced as part of a new linting system for Cargo, controlled by the [lints.cargo] table in Cargo.toml, completing this project goal. See also the other lints that have been introduced.

Reducing Cargo cache collisions

Cargo builds all libraries and binaries in the build-dir and then uplifts final artifacts to the target-dir. At this time, these share a common parent directory. Different build configurations, like --features, can lead to different copies of libraries and binaries in the build-dir. These copies are kept unique by a build-configuration hash but this hash was not always applied due to platform constraints. This can lead to extra rebuilds, missed rebuilds, confusion over what binaries or libraries are used, and so on. These problems get exacerbated when sharing a build-dir across git worktrees.

The build-dir now consistently applies the build-configuration hash to all content by organizing the directories around their build step, rather than their file type, and moving the hash from a file's name to the parent directory.

This work began with the build directory layout project goal in 2025, and its stabilization is a milestone toward a new project goal, unblocking future improvements such as cache garbage collection, cross-workspace cache de-duplication, cross-workspace caching, and fine grain locking.

We previously published a call for testing for the changes that are now taking effect. While this is an internal change, this may break build processes and tests that had workarounds for missing or incomplete features. In some cases, the workaround is no longer needed. See cargo#17287 for possible solutions and to add any new use cases.

Cargo min-publish-age a.k.a. dependency cooldowns

Malicious versions of packages are often caught within hours or days after being published, by either automated scanners or by the community. Rust 1.100 stabilizes Cargo's min-publish-age aware dependency resolution, which lets you wait for that window before it picks up newly published versions. This practice is also known as dependency cooldowns.

You can opt in via .cargo/config.toml:

[registry] global-min-publish-age = "3 days"

When selecting versions, Cargo now skips any version published more recently than that, and tells you what it held back:

$ cargo update Updating crates.io index Locking 2 packages to highest compatible version as of min-publish-age Adding cc v1.11.0 (available: v1.18.0, published 3 hours ago) Adding clap 4.6.7 (available: 4.6.9, published 2 days ago)

When a new version is needed right away, you can override the check for a single update:

$ CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update clap --precise 4.6.9 Updating crates.io index Updating clap 4.6.7 -> clap 4.6.9 (published 2 days ago, minimum age 3 days)

The newer version will be recorded in Cargo.lock and kept from then on until a later cargo update re-resolves it.

A few things to keep in mind:

This depends on the registry recording when each version was published. Versions without a pubtime field in the index are never held back.

cargo install ignores the minimum publish age, for both the installed crate and its dependencies. Pin a version with cargo install foo@1.2.3 if needed.

Cooldowns reduce the risk from some supply chain attacks but are not a complete defense on their own. Please keep reviewing dependency updates as you otherwise would.

Further work to protect the ecosystem is planned under the crates.io supply chain hardening project goal, including quarantine support and automated detection of suspicious releases.

Today, we're open-sourcing Edge0-145B and Edge0-120B, together with our unified inference framework and deployment tools. Edge0-145B is the world's first open-source on-device AI model with 145 billion parameters. It brings coding, reasoning, and agent capabilities that rival frontier cloud models to your own computer.

On-device AI has long forced a tradeoff between model capability and what the hardware can run. Larger models demand more memory, bandwidth, and power; smaller models can struggle with complex work. Moving that work to the cloud adds model-provider fees, data-handling constraints, and a dependence on connectivity.

We're releasing the full stack so developers can reproduce the results, evaluate or fine-tune the models, and integrate them into their own products.

How We Make 100B+ Parameter AI Run on a Personal Computer

Edge0-145B Laptop Performance: Memory, Speed, and Power

Edge0-145B makes a 145-billion-parameter model usable on a personal laptop. A useful local model has to fit in memory, process prompts promptly, generate fast enough to use, and keep power consumption under control. It also needs to sustain longer tasks.

Our earlier Edge0-35B phone release reported peak memory below 2.5GB. On an iPhone 18 Pro Max, Edge0-35B delivers 37+ tokens/s using approximately 2.5GB of memory. Edge0-145B has roughly four times as many parameters; its laptop comparison reports 80+ tokens/s and 28GB peak memory. These measurements apply to different models and hardware.

Why On-Device Models Have Stayed Small

Memory limits kept most on-device models below 10B parameters before September 2026. Apple Intelligence's on-device foundation model had approximately 3B parameters, while Google's Gemini Nano came in 1.8B and 3.25B versions. Even a 7B model could consume approximately 4GB of memory.

Larger models faced a memory wall. Model weights occupy storage and must be read during generation, competing for limited memory and bandwidth with the operating system and other apps. Even an aggressively compressed 35B model could need approximately 20GB of memory, far more than a phone could make available.

Compute, bandwidth, and power created competing constraints. Larger models offered more capability, but strained memory capacity, generation speed, and battery life. Making models smaller helped them fit, often at the cost of capability.

Privacy alone could not close that gap. Apple Intelligence protected user data, but Apple acknowledged that its on-device model was not designed for agentic applications requiring general world knowledge. The prevailing assumption was that on-device intelligence could not match the cloud.

Under the Hood of Edge0: Four Layers of Model and Inference Design

We designed Edge0-145B and its inference engine together to reduce the memory and data movement that make large models difficult to run locally. The design spans architecture, training, loading, and scheduling.

Architecture: share large matrices across sparse experts. Sharing matrices substantially reduces the weights that must be stored and moved while keeping the expert count unchanged. Each group of 64 experts shares two large matrices, while each expert retains a small set of parameters that captures its differences. Previously, every expert stored a complete set of matrices. Of the model's 145B total parameters, only approximately 10B participate in computation on each inference step.

Training: build for local execution from day one. We train the model in its on-device architecture from the outset, with deployment constraints built into its design. This avoids treating local deployment as a compression or pruning step after training a cloud model.

Loading: pipeline GPU memory, system memory, and SSD access. Reading and computation overlap across three storage tiers, avoiding serial waits. Frequently used “hot experts” remain in GPU memory. An expert library of approximately 40GB sits in system memory, with experts brought into GPU memory as needed. Approximately 48GB of vocabulary data resides on the SSD and is read on demand.

Scheduling: use the CPU and GPU together. The GPU computes cached experts while the CPU handles the remaining work in parallel. Speculative decoding verifies multiple candidate tokens at once, spreading the cost of reading weights across more output tokens. These choices support the reported 80+ tokens/s decode rate.

Model and inference-engine design work together to make 100B+ parameter inference practical on personal computers. Source: internal testing.

PostgreSQL Types 101

I started learning with a very simple query. What happens when I run the simplest query SELECT 1337?

While I avoided all the black magic in Postgres internals, I kept this crash course on the basics of data types.

I start with this query.

SET debug_print_parse = on; SELECT 1337;

The database scanner looks at the query, recognises SELECT as a keyword, and 1337 as an integer token. Then it creates a parse tree for the query. Next, PostgreSQL walks the tree and transforms it into a typed query tree.

{QUERY :commandType 1 :targetList ( {TARGETENTRY :expr {CONST :consttype 23 :consttypmod -1 :constlen 4 :constbyval true :constisnull false :location 7 :constvalue 4 [ 57 5 0 0 0 0 0 0 ] } } ) }

Parse tree looks like above. But I just wanted to better understand things like what is the consttype 23 ? why constvalue has [ 57 5 0 0 0 0 0 0 ] and where is my 1337 value ? At this point, I asked Opus 5 to prepare me a full deep-dive course on PostgreSQL types. Spending a few days around there and talking with my agent, whom I named pg_expert taught me these:

consttype = 23 → int4 constlen = 4 → four-byte payload constbyval = true → stored by value constisnull = false → this is not NULL

constvalue 4 [ 57 5 0 0 0 0 0 0 ] can be converted to hexadecimal, making the value easier to recognize:

57 decimal = 0x39 5 decimal = 0x05

On my little-endian system, the bytes were stored least-significant first:

39 05 00 00 → 0x00000539 → 1337

So 1337 had not disappeared. But why do we even have 8 bytes [ 57 5 0 0 0 0 0 0 ] instead of simply 4 bytes ?

That was because constvalue was not declared as an int32. It was declared as a Datum, which was 8 bytes Our value 1337::int4 value stored at the lower four bytes of that generic carrier.

How can that same 8-byte Datum represent a text, an array, or custom types ?

A Datum Does Not Know What It Is

Chatting with my pg_expert agent taught me more. A Datum does NOT know what it represents.

The eight bytes carrying 1337 did not contain a hidden label saying “I am an integer.”. PostgreSQL knew its type only because of this consttype = 23.

That number is an OID (Object IDentifiers) pointing to a row in the pg_type system catalog

SELECT oid, typname, typlen, typbyval, typalign, typinput::regproc, typoutput::regproc FROM pg_type WHERE oid = 23; oid | typname | typlen | typbyval | typalign | typinput | typoutput -----+---------+--------+----------+----------+----------+----------- 23 | int4 | 4 | t | i | int4in | int4out

That means the pg_type row shows what the value means and how PostgreSQL will use it. So far, it’s brilliant and easy to understand. But what about the text type ?

SELECT oid, typname, typlen, typbyval, typinput::regproc, typoutput::regproc FROM pg_type WHERE oid IN ('int4'::regtype, 'text'::regtype) // <== HERE FILTERIN THE INT4 and TEXT only ORDER BY oid; typname | typlen | typbyval | typinput | typoutput ---------+--------+----------+----------+----------- int4 | 4 | true | int4in | int4out text | -1 | false | textin | textout

For text, typlen = -1 means that the representation have a variable length. And typbyval = false means that the Datum carried a pointer.

Datum ──> pointer ──> variable-length text representation

So the same 8-byte value stores a memory address for the text. Datum can pass the value either by value itself or by reference to it. Nice, I love the elegant abstraction Datums provides!

Unknown is a type!

So far everything makes sense, but I wanted to better understand the typinput and typoutput columns too. These functions convert the value provided by the query into a native Datum or vice versa. So I ran this again.

SELECT 1337, pg_typeof(1337), pg_column_size(1337); ?column? | pg_typeof | pg_column_size ----------+-----------+---------------- 1337 | integer | 4

But then I added quotation marks to see if PostgreSQL has dynamic type casting/recognition or something:

SELECT pg_typeof('1337'); pg_typeof ----------- unknown

I was a bit confused at this moment. I initially thought unknown meant “PostgreSQL does not know the type.” So I went back to chatting with my pg_expert agent, who is teaching me everything so far. I learned that unknown is an actual PostgreSQL type with OID 705, used for string literals whose final type hasn’t been decided yet!

Again, this makes super sense because PostgreSQL deliberately assigns untyped string literals this temporary type because the same text could eventually become many different things!

SELECT '1337'::int4;

For example, the query supplies the target type int4. PostgreSQL looked up the typinput function for int4 and called int4in() and when its need to be printer it use int4out()

PostgreSQL converts the unknown literal ‘1337’ through int4in() into a Datum, then returns text through int4out().

Critical Thinking: Wait a Minute! The Type Chooses the Code

Up until this point, typinput and typoutput looked like ordinary conversion mechanism to me. pg_type contained many different native functions for many different types.

While learning more about these functions, one detail stayed with me. An output function did not inspect a Datum and discover its type. It simply trusted all the values and flags around the Datum.

int4out() extracted an integer because PostgreSQL had already selected it as the output function for int4. A different output function could interpret the same generic carrier according to completely different rules.

I still remember that, at that very moment, I was actually thinking about the TOCTOU Vulnerabilities class of the web apps I have been exploiting/fixing for years and years.

“What if I could somehow change the type between the moment PostgreSQL constructed a value and the moment it used that value?”

If I can do this, we might be able to force PostgreSQL to process a Datum created for a completely different type as if it were the type the function expects. Having a type confusion in PostgreSQL can actually give me an opportunity to abuse all the other functions in PostgreSQL internals.

So I went back to learning more about what I can use to force PostgreSQL to natively call different types’ output functions for my int4 value. It turns out that the LANGUAGE internal feature can be used for that purpose.

The LANGUAGE internal allows a superuser to create an SQL function pointing to native code already compiled into PostgreSQL. I created the following one.

SELECT pg_temp.confused_textout(1337); server closed the connection unexpectedly This probably means the server terminated abnormally before or while processing the request.

Uncovering 22-Year-Old PostgreSQL Type-Confusion Primitive

So the idea is simple; I could prepare a query, change something, and execute it later. But change what? PostgreSQL is not gonna let me redefine what the built-in types int4, text, or UUID mean.

CREATE TYPE pg_temp.poc AS ( key uuid );

It had its own type OID, but its attributes defined the current row layout. I can change the attribute a type from UUID to another type without replacing the composite type itself.

The Crash

I created a one-field composite where the attribute started as UUID. Then I prepared a query, changed that attribute to bytea, and executed the prepared statement.

CREATE TYPE pg_temp.poc AS (key uuid); PREPARE pc_crash AS SELECT '(01020000-0000-0000-0000-000000000000)' ::pg_temp.poc; ALTER TYPE pg_temp.poc ALTER ATTRIBUTE key TYPE bytea CASCADE; EXECUTE pc_crash;

And the result was a segfault!

I knew I had found exactly the kind of type confusion I had been looking for!

I knew this was no longer a superuser-only LANGUAGE internal behaviour I had exploited before.

I knew that I could trigger this crash as a lowest-privileged login role on any PostgreSQL instance. Probably all the Postgres-compatible offerings too (more about this later)

Last but not least, I already knew that controlled UUID bytes reaching the wrong native consumer, bytea in my case, had serious exploitation potential. These two have the most reliable exploit primitive I have seen in the PostgreSQL exploits.

Before diving into the Hacking PostgreSQL internals, we need to learn a few things about PostgreSQL to better understand the rest of the article!

Quick Course: What is BYTEA ?

bytea is PostgreSQL’s data type for storing arbitrary binary data. Internally, it uses a variable-length representation called varlena. PostgreSQL places a small header before the bytes to describe their size and storage format.

Basic concepts of bytea +----------------------+------------------------+ | 4-byte header | binary payload | +----------------------+------------------------+

The header tells PostgreSQL which representation it is looking at and how large the complete value is.

We do not need to understand every varlena representation. For the rest of this article, we only need to know two things

Inline representation → the leading bytes can control the claimed length External expanded representation → the leading bytes can introduce an internal object pointer

For example, a normal inline example of the five ASCII characters hello. That 24 can be decoded as 0x24 >> 2 which is 9. So 4-byte header + 5-byte payload = 9 bytes!

+----------------------+------------------+ | 24 00 00 00 | 68 65 6c 6c 6f | | 4-byte header | "hello" | +----------------------+------------------+

The most important example, external representation, when header starts with 01 PostgreSQL believes the value is not stored inline at all. Instead, it treats the bytes as a reference to an expanded object somewhere in memory.

+------------------+---------------------+----------------------------------+ | 01 | 02 | 88 77 66 55 44 33 22 11 | | external marker | expanded-object tag | ExpandedObjectHeader * pointer | +------------------+---------------------+----------------------------------+

So the following data after the header is just object reference pointer instead of the data itself.

Crash and Root Cause Analysis

Lets get back to where we were.

The UUID I supplied contained exactly sixteen bytes, starting with 01 and 02. While attribute a was still UUID, there was nothing special about 01 02 or the fourteen zero bytes following it. They were simply controlled UUID data.

ALTER TYPE changed the current definition of attribute key from uuid to bytea, but it did not convert or rewrite the binary value already stored by the prepared query. During EXECUTE, PostgreSQL still had exactly the same bytes.

When we EXECUTE the query, PostgreSQL need to return the value of our type pg_temp.poc, in order to do that, it calls the composite output function, record_out().

So record_out() looks at the pg_temp.poc’s attribute key and says ‘That is bytea’ and selects byteaout()

But the data byteaout() takes is our old UUID bytes that we can control. This is where the type confusion happens!

byteaout() interprets 01 02 as an external expanded-object header and the following eight zero bytes as a NULL object pointer.

All of these means, we can literally create any varlena representation we want by fully controlling the headers and following 12 byte!

PostgreSQL thinks it needs to reach the ExpandedObjectHeader but its address is 00000000 because thats what we have written inside the UUID, therefore local-backend crash.

Before byteaout() could print the value, it first needed to convert this external representation into something it can print. I learned that PostgreSQL calls this process detoasting.

When we run EXECUTE pc_crash, the call path is as follows. The relevant path looked like this

EXECUTE pc_crash ├─ record_out() a: bytea ├─ byteaout() fetch + detoast ├─ detoast_external_attr() 01 02 → expanded ├─ DatumGetEOHP() eohptr = NULL ├─ EOH_get_flat_size(NULL) └─ NULL->eoh_methods SIGSEGV

PostgreSQL then passed the NULL pointer to EOH_get_flat_size(). The important line inside that function was effectively:

return eohptr->eoh_methods->get_flat_size(eohptr);

eohptr is what we influence and we choose 00000000 in our POC, which is a NULL. Therefore PostgreSQL crashed while trying to read its eoh_methods pointer because it believed it had received a valid external expanded object and followed the normal code path to process it.

The exploitation idea: replacing NULL with our fake object that could make PostgreSQL follow to our own choosen methods!

Hijacking control-flow via Fake ExpandedObjects contains Native Function Pointers

ExpandedObjectMethods contains two native function pointers

typedef struct ExpandedObjectMethods { EOM_get_flat_size_method get_flat_size; EOM_flatten_into_method flatten_into; } ExpandedObjectMethods;

Normal code uses those methods like this to convert an expanded object into its flat representation whenever it’s needed.

EOH_get_flat_size(ExpandedObjectHeader *eohptr) { return eohptr->eoh_methods->get_flat_size(eohptr); } EOH_flatten_into(ExpandedObjectHeader *eohptr, void *result, Size allocated_size) { eohptr->eoh_methods->flatten_into(eohptr, result, allocated_size); }

This is not normally an attacker-controlled callback interface. These are trusted internal representations created by PostgreSQL. The output functions can assume the pointer, header, and methods table are not malicious.

These are indirect native function calls. PostgreSQL obtains the function addresses from the object’s methods table and then calls them. That is something we can actually use to change the control-flow path.

Before going further, I needed a simple model for the objects involved. I named the two fake objects according to what they represented

H = fake ExpandedObjectHeader M = fake ExpandedObjectMethods table

So our plan is that the UUID pointed to H, H pointed to M, and M contained the native function addresses that we wanna cal.

A forged expanded object redirects PostgreSQL’s methods lookup, turning the normal detoasting path into a call to system(H).

Calling system($payload)

The important detail is that PostgreSQL used H twice. Lets remember the actual C code

eohptr->eoh_methods->get_flat_size(eohptr) │ │ │ │ │ │ │ └── argument = H │ │ └───────────── function = system@plt │ └──────────────────────────── methods table = M └─────────────────────────────────────── object = H

First, it treated H as an ExpandedObjectHeader and read the eoh_methods pointer at offset +0x08.

That pointer led to M, where we had placed the address of system(). PostgreSQL then called the selected method and passed the original object pointer, H, as its first argument.

In other words, H helped PostgreSQL find system(), and then the same H was handed to system() as its parameter.

Fortunately, the first eight bytes of H came before the eoh_methods pointer. I could place the NULL-terminated command id>x in those bytes while keeping the address of M at offset +0x08.

Leaking Memory Addresses and defeating the ASLR with the same primitive

As I have heavily talked about exploiting extensions vulnerabilities on managed-Postgres providers at Part 1, we dont get to read /proc/self/mem due to hardening. Our exploitation plan is very clear but the challenge is we need to leak addresses of these objects.

I started to chatting with my pg_expert to find more about PostgreSQL operation that could return a pointer-valued data while SQL expected an ordinary integer. The moment I prompted the agent, it went to

“Oh actually we have talk about this during pg_clickhouse exploit back in July. Do you remember the ClickHouse Array is not a PostgreSQL Array ?”

It was a twist of fate. I had ended up exactly where the original idea had started.

PostgreSQL Arrays store their element type inside their binary representation. unnest() trusts that internal type when deciding how to extract each element.

Normally, everything agrees:

SELECT x FROM unnest(ARRAY['hello']::text[]) AS item(x);

The array says its element is text, so unnest() returns a pointer-valued text Datum and SQL processes it as text.

But what if the array internally says text, while the surrounding SQL contract says bigint ?

Because text is passed by reference, unnest() returns a Datum containing the memory address of the text value! But the surrounding SQL expression expects a by-value bigint, so PostgreSQL prints those same pointer bits as an integer.

In other to say this, we can exploit exactly same type confusion vulnerability to alter the arrays’ text element type to bigint so that unnest() will return the memory address instead of the value! aka leaking memory address!

Creating a PostgreSQL Array data structures with UUID

The smallest PostgreSQL Array needs 48 bytes. A single UUID gives a 16 controlled bytes. So we can simply combine 3 UUIDs next to each other to build exactly 48 byte fully controlled data structer!

Three UUID fields provide 48 controlled bytes: 24 for array metadata, 4 for the text header, 16 for the payload, and 4 filler bytes.

The animation above shows how three UUIDs become one 48-byte array carrier. I prepare those bytes while all three attributes are still UUIDs. From there, I exploit the same type confusion for only the first UUID a to bigint[]!

So unnest() extracts the element as text and returns its pointer, while SQL expects a bigint and exposes that pointer as a memory address. The final +4 skips the text header and lands on my controlled payload.

A direct text to bigint confusion would only reinterpret the old text bytes as an integer. The array was important because it forced PostgreSQL to first produce a real pointer and then expose those same pointer bits as a bigint.
